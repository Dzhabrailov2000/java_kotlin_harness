## Шаг 2. Структура prep-документа

Эталон: `~/IdeaProjects/reactive-uem-architecture/docs/planning/_archive/Reactive_UEM_phase0_planning_prep.md`. Секции нумерованные, дословно:

```
## 1. Цель пилота (держать как рамку)
## 2. Повестка (предложение тайминга, ~60 мин)
## 3. Каркас задач (для груминга и оценки)
## 4. Решения, которые нужно принять на встрече (не оставлять открытыми)
## 5. Риски - поднять заранее, чтобы не всплыли сюрпризом
## 6. Что взять на встречу
## 7. Заметки по итогам (заполнить на встрече)
```

Шапка: H1 вида `# Подготовка к <тип встречи>: <тема>`, подзаголовок с ролью ("Опора для ведущего (архитектор/тех-лид)") и список связанных документов и ADR.

Приёмы, снятые с эталона:

- Повестка с поминутным таймингом, в сумме дающим заявленную длительность.
- Каркас задач размечен приоритетом `**[M]** must для пилота` и `**[L]** можно позже`, разбит на `### ЭПИК N. <название> - владелец: <роль>`, у каждого пункта обязательное пояснение "Зачем:".
- Блок "Как читать" с объяснением терминологии для тех, кто не в контексте.
- Решения даны как явные развилки с рекомендацией автора: "Leshan client против Wakaama или Anjay. Рекомендую Leshan client". Рекомендация обязательна, встреча не место для открытого перебора.
- Раздел 7 это пустой каркас-заглушка с полями "Принятые решения:", "Взятые в спринт задачи / владельцы:", "Открытые вопросы:", "Следующий шаг:".

## Шаг 3. Второй тип prep: стратегия захода

Если у другой стороны уже есть свой план и встреча про стыковку, эталон другой: `~/IdeaProjects/reactive-uem-architecture/docs/planning/_archive/Reactive_UEM_phase0_merge_list.md`. Разделы:

```
## A. Добавить в план команды (наша дельта - этого у них нет)
## B. Закрыть открытые вопросы по безопасности (решения, не задачи)
## C. Зафиксировать в ADR (где их план меняет или подтверждает наши решения)
## D. Подтянуть из их плана к себе (их сильные стороны - принять)
## Как подать на встрече (одна фраза)
```

Установка этого формата: заходить достраивающим и фиксирующим, а не с параллельным планом. Источник истины по задачам реализации это план команды, здесь только дельта и решения. Документ заканчивается заготовленной репликой в кавычках для произнесения вслух.

Спроси у пользователя, какой из двух типов нужен, если из темы не следует однозначно.

Предложи `~/IdeaProjects/reactive-uem-architecture/docs/meetings/` рядом с протоколами, назови это своим предложением, а не конвенцией, и спроси. Не создавай новых каталогов молча.

Связь prep-документа и протокола встречи сейчас ничем не оформлена: в протоколе 2026-06-01 нет ни одной ссылки на два prep-документа к нему, и наоборот. Предложи поставить взаимные относительные markdown-ссылки.

## Шаг 5. Правила оформления

- Пунктуация только ASCII, дефис с пробелами вместо тире.
- Аббревиатуры расшифровывать в скобках при первом упоминании.
- Кросс-ссылки относительными markdown-ссылками вида `](path.md)`, wikilinks не используются.
- Не дописывать непринятые или спекулятивные детали. Развилка это развилка, а не решение. Всё неутверждённое помечать явно.
- Статусы решений не дублировать: ссылаться на `adr/README.md`.
