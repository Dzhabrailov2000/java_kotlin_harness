# Сообщения и обработчики

Сохрани бизнес-эффект при повторе и частичном отказе. В ревью предложи правки;
выполняй их по задаче. Не объявляй доставку однократной по имени настройки.

## Установи гарантии

Найди broker/version, producer settings, consumer isolation, ack/offset policy, retry и
транзакционную границу. Запиши ID события, ключ упорядочивания и внешние эффекты.
Нужные сценарии анализа ниже - методика навыка, не требование использовать Kafka везде.

## Проверь обработку

- **Контракт Kafka:** идемпотентный producer устраняет определенные дубликаты его повторной
  отправки в log; это не обещание однократного бизнес-эффекта произвольного consumer. [S1]
- **Контракт Spring Kafka:** EOS относится к настроенному read-process-write; read и process
  могут выполняться at-least-once. Проверь Kafka-транзакцию и isolation потребителя. [S2]
- **Контракт Kafka:** для эффекта во внешнем хранилище требуется согласовать результат
  с позицией consumer. Kafka transaction сама по себе не делает произвольный HTTP/SQL атомарным. [S1]
- **Паттерн Richardson:** записывай ID обработанного сообщения и бизнес-эффект в одной
  транзакции, если выбран DB inbox. Раздельный check-then-insert не является этим протоколом. [S3]
- **Паттерн Richardson:** outbox связывает изменение БД и запись события в одной транзакции;
  relay может публиковать повторно. Consumer все равно должен выдерживать нужные повторы. [S4]
- **Контракт Kafka:** порядок задается внутри partition. Если нужен порядок одного объекта,
  проверь partition key и все стадии обработки, включая параллелизм и retry. [S1]
- **Выбор навыка:** определи судьбу poison message, предел повторов, диагностику и replay.
  Перенос в DLT не называй успешным бизнес-исполнением; сохрани возможность расследования.
- **Выбор навыка:** для дедупликации задай scope ID и срок хранения по реальному горизонту
  повторов. Для исправленного payload не переиспользуй старый ID без определенного протокола.

## Пример паттерна, не универсальный SQL

Адаптация Idempotent Consumer Richardson. [S3]

~~~text
BEGIN
  записать (consumerId, messageId) под UNIQUE/PRIMARY KEY;
  выполнить изменение бизнес-данных;
COMMIT
после успешного завершения разрешить ack/commit offset по API listener;
~~~

Повтор после DB commit, но до ack, должен распознаваться. При конфликте ключа выбери поддерживаемый
путь БД/transaction manager; не продолжай работу в уже испорченной транзакции. Схема не решает
однократность внешнего HTTP-эффекта внутри блока. [S1] [S3]

## Проверь

Проверь повтор того же ID, два конкурентных consumer, сбой до commit и потерю ack после commit.
Для порядка проверь путь retry/replay. Используй изолированный брокер/БД подходящей версии,
если изменение зависит от их гарантий. В находке покажи последовательность событий и неверный эффект.
