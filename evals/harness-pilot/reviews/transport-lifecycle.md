# Граница жизненного цикла HTTP-регистратора

Подтверждено: выход из Recorder не дожидается daemon-потоков отдельных HTTP-запросов и не отменяет их upstream-операции. Старый локальный обработчик может продолжать ожидание после завершения CLI и позже выдать ошибку. Фактическое перекрытие серверных вычислений модели и расход таких запросов этим не установлены.

## Основание по исходникам

`transport.py:92-103` создает стандартный ThreadingHTTPServer и при выходе вызывает shutdown, server_close и join только потока serve_forever. Ссылки на отдельные обработчики и их upstream-соединения не сохраняются для отмены.

Проверена установленная стандартная библиотека Python 3.9.6:

- `http/server.py:144`: ThreadingHTTPServer задает daemon_threads=True.
- `socketserver.py:689`: process_request создает отдельный поток обработчика с этим daemon-флагом.
- `socketserver.py:635`: _Threads.append исключает daemon-потоки из списка ожидаемых потоков.
- `socketserver.py:699`: server_close ждет только потоки из этого списка. Они не включают текущие HTTP handlers.
- `socketserver.py:244`: shutdown останавливает цикл serve_forever, а не активные handlers.
- `socketserver.py:477`: TCPServer.server_close закрывает слушающий сокет. Это не команда закрыть все исходящие соединения обработчиков.
- `socketserver.py:370`: необработанная ошибка handler выводится в stderr через handle_error. В текущем регистраторе к ней не добавляется номер сохраненного запроса.

Полные локальные пути библиотеки:

- `/Library/Developer/CommandLineTools/Library/Frameworks/Python3.framework/Versions/3.9/lib/python3.9/http/server.py`
- `/Library/Developer/CommandLineTools/Library/Frameworks/Python3.framework/Versions/3.9/lib/python3.9/socketserver.py`

`transport.py:68` вызывает opener.open без явного timeout. `transport.py:84` может блокироваться в read1. Пока эти операции ждут, handler не доходит до записи в клиентский сокет и не замечает закрытие клиента через BrokenPipeError. Очистка `with response` происходит только после выхода из его блока. На проверенном локальном Python глобальный socket timeout равен None; это не обещание бесконечного ожидания, поскольку сеть и удаленный узел могут завершить его сами.

## Локальное воспроизведение без сети

Сохранены [mock](transport-lifecycle-probe.py) и [полный вывод](transport-lifecycle-output.txt).

Рабочий каталог: `/Users/dzabrailovramzan/IdeaProjects/java_kotlin_harness/evals/harness-pilot`.

Точная команда:

```sh
python3 -B reviews/transport-lifecycle-probe.py > reviews/transport-lifecycle-output.txt 2>&1
```

Mock использует неизмененный Recorder и его реальный Handler.forward. Прием соединения, listening socket, opener и response заменены объектами в памяти. Реальные унаследованные ThreadingMixIn.process_request/server_close и daemon-thread учет сохранены. Создание socket и socket.create_connection дополнительно заменены функцией, которая немедленно падает: случайное сетевое обращение невозможно. Изменения модулей относятся только к новому процессу этого теста; текущий runner и его процессы не затрагиваются.

Проверены две фазы:

| Фаза ожидания | Recorder.__exit__ вернулся | Поток serve_forever завершился | Handler остается жив | После явного освобождения mock |
| --- | --- | --- | --- | --- |
| opener.open | да | да | да, daemon | создал 0000-error.json после выхода Recorder |
| response.read1 | да | да | да, daemon | выбросил IncompleteRead после выхода Recorder; затем response был закрыт |

Во второй фазе response не был закрыт на момент возврата Recorder.__exit__. Позднее исключение принято реальным механизмом process_request_thread; тестовый handle_error сохранил его тип вместо печати traceback. В текущем настоящем сервере этот путь выводит traceback в общую stderr. После теста оба mock-handler освобождены и завершены, временные каталоги удалены.

Это доказательство возможности по реальному коду управления потоками. Оно не использует реальный upstream-сокет и не является наблюдением за живыми соединениями текущей серии.

## Влияние на трактовку серии

Последовательный запуск CLI означает последовательность клиентских процессов. Он не гарантирует, что все локальные HTTP handlers предыдущей попытки уже закончились. В пределах одного живого процесса runner старый daemon-handler может сосуществовать с новой попыткой. Аналогично, повтор внутри одного CLI может начаться, пока обработчик прежнего запроса еще ждет upstream.

Это позволяет поздней ошибке общей stderr принадлежать старой попытке. По времени получения сообщения без request id нельзя надежно приписать его R18 или конкретному запросу. По имеющимся материалам здесь не устанавливается, какие именно реальные обработчики перекрывались.

`run.py:95` фиксирует время завершения CLI до выхода из Recorder. Позднее ожидание handler не добавляется к этому времени. Handler также может позже дописать HTTP-артефакт после создания result.json, поэтому производная транспортная сводка является временным срезом, пока эти операции не завершились.

Живой локальный поток, блокирующийся вызов или сохраненный HTTP 200 не доказывают, что поставщик продолжает считать ответ. Нельзя установить завершение/отмену серверного вычисления, расход незавершенного запроса или биллинг без дополнительных серверных доказательств. Не следует добавлять предполагаемые токены или вычитать предполагаемое время из основных результатов.

Текущие основные баллы не меняются. Ограничение относится к силе утверждений о неперекрытии транспорта, причине задержек и полноте учета расхода. Одно клиентское испытание остается одним trial независимо от числа его транспортных попыток.

## Следующая версия

Нужно дать регистратору явное владение активными запросами и их соединениями: сохранять локальный request id, фазу, время начала/окончания, состояние завершения и причину отмены. На закрытие downstream или завершение CLI прекращать соответствующее upstream-ожидание, закрывать/отменять активное соединение и ждать завершения handler перед финализацией транспортных артефактов. Само выставление daemon_threads=False недостаточно: оно способно лишь превратить незавершенную операцию в бесконечное ожидание server_close.

Поскольку opener.open скрывает соединение до получения ответа, следующему транспорту нужен доступ к отменяемому соединению и во время ожидания заголовков. IncompleteRead, его partial bytes и прочие ошибки чтения надо сохранять под номером запроса; не ограничиваться общим traceback. Состояние "локально отменено" не следует называть подтвержденной отменой вычисления на сервере.

Это очистка принадлежащих регистратору операций после прекращения клиентской работы, а не новый лимит времени или токенов модели. Рекомендация относится только к следующей версии. Замороженный runner, входы, текущие процессы и сеть не изменялись.
