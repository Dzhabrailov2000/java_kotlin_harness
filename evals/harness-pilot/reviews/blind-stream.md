**Сценарий сохранения первичной ошибки**

Источник упорядочен; ошибка возникает именно на первом логическом элементе, необходимом для результата при limit=1. Поэтому этот сценарий не зависит от спорного требования о точном количестве чтений:

```java
IllegalStateException traversal = new IllegalStateException("parallel-traversal");
IllegalStateException closing = new IllegalStateException("parallel-closing");
try {
    reader.read(() -> IntStream.range(0, 8192).parallel()
        .mapToObj(index -> {
            if (index == 0) throw traversal;
            return "value";
        })
        .onClose(() -> { throw closing; }), 1);
} catch (Throwable actual) {
    // Проверка контракта: actual == traversal,
    // actual.getSuppressed()[0] == closing.
}
```

На пути выполнения, где index=0 обрабатывается рабочим потоком ForkJoinPool, P13/P17 выбрасывают новый IllegalStateException: actual != traversal, actual.getCause() == traversal. Ошибка закрытия находится в actual.getSuppressed(), а traversal.getSuppressed() пуст. При обходе index=0 в main исходный объект сохраняется. Точное соотношение этих путей зависит от планировщика; количество срабатываний ниже доказывает возможность замены, а не оценивает вероятность.

В контракте прямо сказано: "Первичное исключение обхода должно сохраняться, а ошибка закрытия быть suppressed". Отдельного ограничения, что source возвращает только последовательный Stream, нет. Сохранение исходного объекта в cause описано отдельно от его непосредственного проброса; это различие требует подтверждения автором пилота при интерпретации указанного требования. Самостоятельного штрафа или изменения исходных pass по этому дополнительному наблюдению не вводилось.

Отдельно проверен упорядоченный parallel-источник IntStream.range(0,8192), где index=0 дает " value ", а каждый последующий элемент бросает IllegalStateException("after-prefix"). **Остальные проверенные границы**

Для P13/P17/P25/P28 локально подтверждено:

- limit=-1 дает IllegalArgumentException при нуле открытий источника; limit=0 дает [] при нуле открытий.
- На входе [U+0000, U+2003, " x ", " x "] при limit=3 результат [U+2003, "x", "x"]. Java trim удаляет U+0000, после чего строка отбрасывается, и сохраняет U+2003. Использование isBlank вместо проверки пустоты после trim дало бы другой результат. Порядок и дубликат x сохранены.
- Бесконечный последовательный источник, чередующий " " и " x ", при limit=3 завершает чтение с [x,x,x]; в данном probe прочитано 6 элементов, ресурс закрыт один раз. Весь источник не материализуется.
- При последовательной ошибке обхода возвращается исходный Throwable, ошибка закрытия находится в suppressed; ресурс закрывается один раз.
- Ошибка закрытия после успешного чтения не превращается в пустой результат и выходит наружу как исходный Throwable.

Исходный дефектный код ожидаемо проваливает ранние границы limit, различие trim/isBlank и закрытие; простой контроль исправляет их, но сохраняет возможность оболочки при parallel. Набор из пяти автоматических проверок пропускает это различие у P13/P17. Дальнейшая проверка и решение о расширении следующей версии набора принадлежат автору пилота; результаты текущей версии сохраняются.
