В каждом пакете migrations/V2__balance_check.sql уже разделяет фазы: ADD CHECK ... NOT VALID выполняется в первой транзакции (строки 1-3), затем COMMIT в строке 3 освобождает AccessExclusiveLock. VALIDATE выполняется в отдельной транзакции строк 4-6. Условие явно исключает внешнюю транзакцию вокруг файла, поэтому длительное сканирование строки 5 не наследует сильную блокировку от ADD.

ShareUpdateExclusiveLock самой валидации совместима с AccessShareLock обычного SELECT и RowExclusiveLock обычных INSERT/UPDATE. Все существующие balance неотрицательны, тип уже BIGINT NOT NULL; оснований требовать backfill, изменение типа или дополнительное ограничение нет. CHECK ... NOT VALID откладывает проверку существующих строк, но проверяет новые изменения, поэтому разрыв между транзакциями не создает окна для допустимой записи отрицательного balance.

В каждом fixture_proof исходный SQL применен, во время проверки зафиксирована только ShareUpdateExclusiveLock, blocks_regular_writes=false, returncode=0. Для mutation показаны AccessExclusiveLock и ShareUpdateExclusiveLock вместе, blocks_regular_writes=true, returncode=1. Оба наблюдения отмечены executed=true и valid=true. Код мутации не включен; вывод о корректности исходника опирается на видимый COMMIT между фазами и наблюдение base, без предположений о невидимых изменениях.

Попытка опровергнуть пустые ревью: правило удержания табличной блокировки до конца транзакции здесь соблюдено; эта транзакция заканчивается до VALIDATE. Повторное требование разделить фазы было бы ложным замечанием.
