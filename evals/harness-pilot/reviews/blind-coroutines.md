**Проверка граничных сценариев и попытка опровержения**

Для P11/P16/P21 по коду прослежены следующие случаи; это не дополнительные выполненные тесты:

- ids = [b, a, b] с разным временем завершения fetch дает результаты в порядке [b, a, b]; повтор b создает отдельный вызов и отдельную позицию результата.
- При parallelism=2 и трех приостанавливающихся вызовах только два держат permit; третий ожидает освобождения. async запускаются до общего ожидания, поэтому реализация допускает перекрытие вызовов и не сериализует всю загрузку.
- IOException для a дает Failed(a), остальные элементы продолжают обрабатываться. CancellationException или IllegalStateException для a выходят к вызывающему; общего catch для Throwable нет.
- parallelism=0 или -1 вызывает IllegalArgumentException до клиента, в том числе при пустом ids. Пустой ids при положительном parallelism возвращает пустой результат без клиентских вызовов.
- Отмена во время ожидания permit или fetch проходит через структурированные дочерние задачи; withPermit освобождает полученный permit, а Failed для отмены не создается.

Создание одной async-задачи на элемент не нарушает заданный предел: контракт ограничивает одновременные вызовы клиента, а не количество ожидающих корутин. Требования принудительно выделять потоки для несуспендирующего клиента или ограничивать суммарную конкурентность между разными вызовами load в задании нет; такие условия не добавлялись к оценке.

Пропущенный тестами дефект с воспроизводимым входом не установлен. По счетчикам пяти тестов нельзя подтвердить полноту покрытия. Включенный fixture_proof фиксирует 4 failures у исходного варианта и 0 у эталона; это доказательство из пакетов, а не новый прогон данного ревью.
