# Следующий эксперимент [Проект]

Эта серия не запущена. Пилотные задания после просмотра результатов больше не являются отложенной
выборкой. Их можно оставить как регрессионные тесты запускателя и использовать для настройки.

## Перед следующим изменением обвязки

1. Сохранить текущие файлы как неизменяемый baseline (исходный вариант) с хешами и точными
   model ID/effort. Результат этого пилота относится к snapshot/, а не к будущей активной установке.
2. Заранее сформулировать одну гипотезу: например, сокращение навыка ошибок сохранит корректность
   и уменьшит расход. Создать новый снимок с этим изменением.
3. Сравнить текущую и измененную обвязку на одном клиенте, с одинаковыми инструментами и заданиями.
   Условие без персональной обвязки оставить отдельным ориентиром. Одно сравнение "без/с" не
   отвечает на вопрос, улучшила ли следующая правка уже существующий пакет.
4. До ответов зафиксировать критерии принятия и браковки. Исполняемые проверки поведения, отсутствие
   новых ложных critical/major и стоимость показывать раздельно. Численные пороги выбрать исходя из
   реальной цены ошибок и квоты; пилот не установил универсальный допустимый процент регрессии.
5. Проверить оценщик на эталоне и мутациях, затем запустить новые отложенные задачи и все повторы.
   Решение об изменении принимать по сохраненным результатам, включая неудачи и ограничения.

Дополнение после пилота: для T04 выяснилось, что frozen-тесты и эталон не проверяют сохранение
исходного объекта исключения из parallel Stream. В новой версии отдельно определить эту гарантию
и допустимость дополнительного обхода. Не добавлять обязательный sequential задним числом и не
пересчитывать старые баллы по новым требованиям; доказательства в posthoc-findings.json.

Дополнительный HTTP-тест T01 также воспроизвел преобразование числового/boolean accountId в строку
у одного решения и самого эталона. В следующем контракте явно определить допустимость такого
преобразования и проверить ее на HTTP-границе. Исходные баллы не менялись; доказательства в
reviews/rest-json-probe/observations.json. Отдельный DTO без проверки настроек mapper не доказывает
строгость JSON-типов.

Перед большой серией отдельно проверить устойчивость передачи длинных ответов Claude в том же
режиме max. В пилоте наблюдались незавершенный поток ответа, fallback без stream и api_retry;
точная причина разрыва не установлена. Сначала воспроизвести и локализовать проблему на уровне
клиента/регистратора/прокси/поставщика. Записывать ошибки чтения вместе с ID запроса. Полный расход
оборванных запросов не восстанавливать догадкой из итогового usage клиента. См. transport-events.md
и transport-observations.json. Эти события не вычитаются из времени текущего пилота.

Локальный probe также подтвердил, что HTTP handlers могут пережить Recorder.__exit__. Следующая
версия должна владеть активными соединениями, отменять их при прекращении клиентской работы и
дожидаться локального завершения перед фиксацией артефактов. Это очистка ресурсов, а не ограничение
времени работы модели. Одна замена daemon_threads=False проблему не решает: server_close может
просто зависнуть. Доказательства и границы вывода: reviews/transport-lifecycle.md. Продолжение
серверного вычисления из существования локального потока не следует.

Официальная [документация Claude API о длинных запросах](https://platform.claude.com/docs/en/api/errors#long-requests)
рекомендует потоковую передачу для долгих ответов и предупреждает о разрывах неактивных соединений
при большом max_tokens без streaming. Это основание проверить транспорт, а не доказательство
причины конкретного сбоя пилота. Для формата и завершения событий используется
[описание streaming Messages](https://platform.claude.com/docs/en/build-with-claude/streaming).
Число повторов и таймауты обычных SDK нельзя автоматически приписывать Claude Code: настройки
и фактические события CLI в этой серии сохранены отдельно.

## Разделить три вопроса

1. Помогает ли текущая установка в обычной работе? Свежая задача, естественный выбор навыков,
   сравнение с отсутствием персональной обвязки. Это вопрос пилота.
2. Помогает ли содержание конкретных навыков? Заранее выбрать релевантный навык для задачи и явно
   вызвать его в дополнительном условии C. A, B и C получают одинаковый контракт. Выбор навыка
   фиксируется до ответов; нельзя добавить подсказку только после неудачи модели.
3. Правильно ли выбирается навык? Отдельные релевантные, нерелевантные и неоднозначные запросы;
   измерить необходимые и лишние срабатывания. Выбор не заменяет проверку конечного кода.

Не следует одновременно переписать навыки, изменить модель, включить workflow и увеличить лимиты,
а затем приписывать улучшение одному из этих изменений. Каждое изменение - отдельный снимок и
заранее названная проверяемая гипотеза.

Ниже темы, а не готовые задания и не гарантированно достаточный размер выборки. Для каждой нужны
конкретный контракт, исходники, исполняемая проверка, эталон и мутации, которые проверка отвергает.

## Сбор и анализ

- Начальная расчетная серия: 30 задач x 3 повтора x 2 клиента x 2 условия = 360 попыток.
  Число повторов и стоимость уточняются по пилоту до старта, а не после просмотра победителя.
  Два условия могут быть "без/с" либо "текущая/измененная" для заранее выбранного вопроса.
  Если в той же серии нужен третий вариант (например, явный вызов навыка или дополнительный
  ориентир без обвязки), это уже 540 попыток. В текущий план запуска они не включены.
- Пары A/B используют одинаковый base commit, tools, зависимости и критерии. Порядок перемешан,
  повторы разделены во времени. Каждая попытка получает свежий контекст.
- Основные показатели: функциональное выполнение, найденные дефекты и ложные замечания на чистом
  коде. Качество чтения и структуры проверяется вслепую отдельно от соблюдения формальных правил.
- Сравнивать разницу внутри каждой задачи. Интервалы неопределенности считать с группировкой по
  задаче: три повтора одного задания не превращают его в три независимые предметные задачи.
- Отдельно показывать ошибки окружения, незавершенные попытки, неверную загрузку инструкций и
  отсутствие активации навыка. Сбой нельзя молча удалить из знаменателя или заменить лучшим ответом.
- Не объединять разные model ID/effort и версии навыков в одну цифру. Смена версии запускает новую
  серию. Сохранить удачные, неудачные и противоречащие гипотезе результаты.
- Перед принятием отдельного правила добавить абляцию: убрать только это правило, оставив остальные
  компоненты и задачи прежними. Пользу пакета нельзя автоматически приписать каждому его файлу.

Основания методики и ссылки - в PROTOCOL.md. Конкретный корпус и дизайн анализа здесь предложены
для этой обвязки и требуют валидации исполнимости, как и задания пилота.
