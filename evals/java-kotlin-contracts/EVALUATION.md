# Проверка навыка контрактов

Подготовлены входы и критерии для будущего сравнения поведения. Модельные прогоны не выполнены.
Проверка структуры навыка, ссылок и JSON не доказывает полезность инструкций для модели.

## Состав

- `cases.json`: 18 входов для ревью и одной разрешенной правки. Передавай модели только context,
  request и files выбранного случая.
- `rubrics.json`: критерии оценщика, отдельно от входа испытуемой модели.
- `routing.json`: 4 проверки выбора навыка. Передавай только request, скрывая expected.
- [CP01-CP08](ORIGINS.md): примеры из открытого кода
  на закрепленных коммитах. DBC, VALUE, EQUALITY, MODEL и FAILURES раскрыты в
  [contract-design.md](../../skills/java-kotlin-contracts/SKILL.md).
  TYPES, VALIDATION и ATOMICITY раскрыты в
  [jvm-boundaries.md](../../skills/java-kotlin-contracts/SKILL.md).

| Случаи | Что проверяют |
|---|---|
| C01-C04 | Допустимые границы, пустота, знак и неизвестные бизнес-требования |
| T01-T03 | Различие типов, aliases и сохранение снимка |
| E01-E02 | Равенство чисел и значимость представления |
| V01-V02 | Реальная проверка вместо декларации DSL или отключаемого assert |
| F01-F03 | Состояние после отказа, неопределенный внешний эффект, допустимая повторная попытка |
| A01-A02 | Повторяемая CAS-функция и ограничение в общей БД |
| B01-B02 | Граница builder и фактическое включение Spring validation |

Девять случаев содержат проблему, шесть корректны, два требуют недостающего контекста,
один требует изменить файл. Это адаптированные учебные фрагменты по публичным контрактам,
а не найденные дефекты библиотек. Код пользователя и корпоративных проектов не использован.
Фрагменты не являются общим компилируемым проектом: часть намеренно опускает imports,
зависимости и реализации соседних API. Не объявляй сборку проверенной по чтению текста.

## Протокол сравнения

1. Зафиксируй точный model ID, effort, версию клиента, общие инструкции, настройки и снимок навыка.
   Сравни одну модель в свежих контекстах A без навыка и B с единственным SKILL.md навыка.
   Остальные инструкции и инструменты должны совпадать; исключи скрытое подключение навыка в A.
2. Создай файлы случая в отдельном временном каталоге. Не открывай модели rubrics, EVALUATION.md,
   соседние случаи и ответы предыдущих запусков. Для функциональной проверки B явно подключи
   навык, а выбор навыка проверь отдельно через routing. Не передавай ожидаемый вывод подсказкой.
3. Для ревью проверь отсутствие правок и оцени конкретные сценарии нарушения. При корректном
   решении оцени отсутствие ложных замечаний. В C04 и B02 проверь честную границу знания,
   а не число вопросов или уверенность формулировки.
4. В F01 проверь настоящий diff, а не текст обещанного патча: прежний port сохраняется при ошибке,
   значения 1 и 65535 принимаются, 0 и 65536 отклоняются; тип ошибки, сообщение и возврат this
   сохранены. Используй доступный Kotlin toolchain для исполнения либо отметь, что оно не проверено.
   Один и тот же исполняемый fixture, если он подготовлен, должен использоваться в A и B.
5. Оцени must/must_not по смыслу. Принимай разные решения, которые обеспечивают заданный контракт.
   Не требуй определенных имен, одного вида класса, максимального количества проверок или
   совпадения с эталонным патчем. Для T01 важен запрет смешения типов, для E01 - согласованность
   равенства и hashCode, для A02 - защита общей БД от конкуренции.
6. Сохрани ответы, реальные diff, команды и результаты проверок, ложные находки, пропуски,
   опасные рекомендации, затраты времени и контекста. При неоднозначности повтори пару в новых
   контекстах. Не приписывай единичному удачному ответу стабильный эффект навыка.

Рабочий критерий первого сравнения: сохранить шесть корректных решений, не выдумать требования
в пограничных случаях, исправить F01 в рамках задачи и выявить подтвержденные нарушения.
Вредные советы учитывай даже без физического изменения файла: запрет разрешенных входов,
сломанное равенство, повтор внешнего эффекта, утрата снимка или ложная гарантия атомарности.
Пользу оцени относительно A: меньше таких ошибок или больше полезных находок без роста вреда.

Все случаи открыты при разработке и пересекаются с примерами навыка. Перед окончательным
принятием добавь независимые задачи из других публичных API, зафиксированные до дальнейшей
настройки. Этот набор не является закрытым тестом способности обобщать.

## Почему skill

Установление бизнес-контракта требует контекста. Hook может запустить уже принятую проверку,
а compiler, тест или constraint БД - обеспечить конкретное ограничение. Они не выводят
требования из предметной области. Отдельный агент не нужен для загрузки этих инструкций.

Структура соответствует [Agent Skills specification](https://agentskills.io/specification) и
[Anthropic authoring guidance](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices):
самодостаточный файл, конкретные примеры и оценка на задачах. Имя модели не встроено в инструкции;
смена модели требует нового сравнения, а не предположения, что императивный текст стал детерминированным.
