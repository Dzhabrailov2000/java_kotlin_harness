# Проверка навыка нейминга

Корпус подготовлен для сравнения поведения модели. Он не является отчетом о пройденных модельных
тестах. Проверка YAML, ссылок и JSON подтверждает структуру, а не качество рекомендаций.

## Материалы

- `cases.json`: 24 входа - 8 проблемных, 8 корректных, 8 с ограничениями контрактов. Последние включают
  два разрешенных переименования. Поля `context`, `request` и `files` предназначены испытуемой модели.
- `rubrics.json`: критерии оценщика, происхождение примеров и недопустимые действия. Не передавай
  этот файл испытуемой модели. `acceptable_names` содержит примеры, а не закрытый список ответов.
- `routing.json`: 4 отдельных запроса для проверки выбора навыка. Ожидаемый ответ видит только оценщик.
- [Открытые исходники](ORIGINS.md): расшифровка OS01-OS20
  и ссылки на конкретные коммиты. В этом корпусе нет кода из личных или корпоративных проектов.

Фрагменты адаптированы для изоляции конкретного решения. Проблемные имена в основном внесены
намеренно; не приписывай их исходным библиотекам. Фрагменты не составляют готовый Gradle/Maven-проект.
Заявления о компиляции потребуют отдельного запуска в подходящем окружении с зависимостями.

Все 24 случая - открытый корпус разработки. Они пересекаются с примерами навыка и не измеряют
обобщение на неизвестный код. Для итогового принятия добавь независимую выборку из других публичных
API, не использованную при настройке инструкций; зафиксируй ее до просмотра результатов.

## Сравнение

1. Зафиксируй точный model ID, effort, версию клиента, настройки, общие инструкции и снимок навыка.
   Для текущей основной модели пользователя сначала сравни ее с собой, затем повторяй при смене модели.
2. Выполни два запуска в свежих отдельных контекстах: A - та же обвязка без этого навыка,
   B - та же обвязка с единственным SKILL.md навыка. Остальные условия должны совпадать.
   В функциональной проверке явно подключи навык к B; автоматический выбор проверяй отдельно.
3. Передай только вход выбранного случая. Размести файлы в изолированном временном каталоге;
   не давай модели доступ к `rubrics.json`, предыдущим ответам и полному дереву evals.
4. Для `review` проверь отсутствие изменений файлов. Для `rename` разреши только указанный rename
   с сохранением контракта. Сравни реальный diff, а не обещание в ответе.
5. Оцени ответ по смысловым критериям. Не требуй совпадения строки с одним эталонным именем.
   Отдельно учитывай ложные замечания, пропущенные ограничения и непрошеные изменения.
6. Если результат неоднозначен или нестабилен, повтори соответствующие пары в новых контекстах.
   Сохрани сырые ответы и результаты, не подбирай после запуска удобный критерий успеха.

Для проверки выбора навыка используй только `request` из `routing.json`, без имени навыка и без
подсказки ожидаемого выбора. Положительные и отрицательные случаи должны иметь одинаковые условия
обнаружения. В реальной сессии проверь фактическую загрузку; список навыков в CLI ее не доказывает.

Минимальная запись результата: `case_id`, A/B, точная конфигурация модели, загружен ли навык,
ответ, diff, выполненные проверки, полезная находка, ложная находка, нарушение контракта,
непрошеная правка, время и расход контекста. Не заполняй отсутствующие измерения предположениями.

Предлагаемый порог первого эксперимента: ни одного нарушения обязательного контракта или границ
правок; не больше одного необоснованного замечания на восьми корректных случаях; полезных находок
больше, чем без навыка, либо меньше ложных при сохранении полезных. Это рабочий критерий этого
эксперимента, не заявленная точность и не общеотраслевой стандарт. Если A уже решает все случаи,
добавь более различающую независимую выборку, а не объявляй пользу доказанной.

## Почему навык устроен так

- [Agent Skills specification](https://agentskills.io/specification): YAML `name`/`description` и
  Markdown-инструкции; фиксированной схемы разделов тела нет. В этом комплекте все инструкции и примеры находятся в одном SKILL.md.
- [Anthropic: Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices):
  короткие инструкции, конкретный триггер, примеры и проверка на целевых моделях. Название модели
  не определяет правила предметной области.
- [Anthropic skill-creator](https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md):
  императивная форма полезна для действий; существенные причины важнее повторения MUST/ALWAYS.
- [Thariq Shihipar, Claude Code team](https://claude.com/blog/lessons-from-building-claude-code-how-we-use-skills):
  дополнительные материалы и наблюдаемые ошибки полезнее пересказа базовых знаний модели.
- [Boris Cherny, Ramp office hours](https://claude.com/customers/ramp-boris-office-hours):
  проверка новых моделей на повторяемом наборе задач. Это основание для сопоставления, не стандарт
  оформления SKILL.md и не авторство инструкций этого навыка.
- [Andrej Karpathy, Verifiability](https://karpathy.bearblog.dev/verifiability/): проверяемость результата.
  В этой задаче механические ограничения проверяются инструментами, качество смысла - критериями
  на коде. Статья не предписывает формат навыков или конкретные правила Java/Kotlin.

У навыка определены шаги и критерии, но он не становится детерминированным от императивного текста.
Регистр, ссылки и часть контрактов проверяемы механически; выбор точного доменного имени остается
контекстным решением. Компенсаторы особенностей модели добавляй после воспроизводимой ошибки,
а не по предположению о новой версии.
