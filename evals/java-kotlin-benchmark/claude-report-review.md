## Закрытые major замечания

### 1. Ответ Codex не сверялся с сырым ответом клиента

В исходной версии `validate_results.py:21-34` проверялось совпадение `answer.txt` и `answer.json`, но не их соответствие `item.completed/agent_message` из `stdout.txt`. Подмена verdict одновременно в двух разобранных файлах принималась `validate_call`, хотя исходный поток клиента содержал другой verdict. Это позволяло ошибке разбора или дрейфу артефактов пройти проверку происхождения ответа.

В исправленной версии `validate_results.py:27-29` требуется ровно одно завершенное сообщение и равенство его JSON сохраненному ответу. Повтор той же подмены завершился ожидаемой ошибкой `Codex answer differs from raw CLI output`. Проверка применяется к ответам испытуемой модели и оценщика. Полная проверка сохраненной серии Codex по-прежнему проходит.

### 2. HTML мог получить ложную зеленую проверку при неверной модели

Исходная версия `validate_results.py:165-166` сверяла числовые показатели и строки, но пропускала `run_config`, `display` и сведения о моделях. Воспроизведение: взять свежий результат `summarize`, в памяти заменить `run_config.model` и пользовательскую подпись серии на вымышленный Claude, оставить реальные Codex оценки и встроить данные в шаблон HTML. Полная проверка принимала такой отчет. Для отчета с двумя моделями это нарушало существенную границу вывода: правильные числа могли быть приписаны другой модели.

В исправленной версии `validate_results.py:168-173` сверяются также идентификаторы серии/модели, описания, протоколы, анализ, план отбора и учет диагностических запусков. Повторные раздельные подмены `run_config`, `display` и суммы диагностических запусков теперь отклоняются. Для первых двух получены ошибки `Stale report: run_config` и `Stale report: display`.

## Отдельное ревью заключения по внешнему аудиту

В проверенных существенных выводах `AUDIT_RESPONSE.md` подтвержденных ошибок critical/major не найдено. Это проверка возражений и подтверждений аудита по исходному снимку, а не повторное ревью всех навыков или сервисов UEM.

Рассмотренные документы:

- `AUDIT_RESPONSE.md`: SHA-256 `d70a845df724456c26bf3049a635d7d0f785e35d0e51bcce446111d0f3ec1f50`.
- Внешний `~/.local/share/code-reviews/jk-skills-audit-2026-10-06/SUMMARY.md`: SHA-256 `74f6a9d01bc49475307a80086841f386be5d956d4f2b91939f43186a9226c820`.
- `junit-audit-check.json`: SHA-256 `aba834b94bbca8a1d2c513ef4eea0ea912fe3f795c718e7917280d948b24b08c`.

Сильнейшие проверенные основания:

1. **JUnit.** В замороженном testing:75 действительно дан `assertThrowsExactly<InvalidRecordException> { ... }`. Независимо прочитаны `Assertions.kt` и `Assertions.java` из локальных source jars JUnit 6.0.3 и 5.13.4: Kotlin-обертки есть для `assertThrows`, но не для `assertThrowsExactly`; все Java overloads точной проверки требуют `Class<T>` первым аргументом. Сохраненный `junit-audit-check.json` содержит ожидаемое отклонение первой формы и успешную компиляцию формы с `InvalidRecordException::class.java`. Вывод о неверном примере стандартного API обоснован. Компиляция в этой отдельной линзе повторно не запускалась; версия Kotlin в сервисах этим не подтверждается.

2. **SQL и граница транзакций.** В frozen sql-migrations:62-64 две команды стоят в одном блоке без COMMIT, а строка 69 требует лишь разделения шагов rollout. По непосредственно прочитанным [PostgreSQL 18 ALTER TABLE, Notes](https://www.postgresql.org/docs/18/sql-altertable.html#SQL-ALTERTABLE-NOTES), NOT VALID позволяет немедленно завершить транзакцию добавления, после чего отдельный VALIDATE берет SHARE UPDATE EXCLUSIVE. [Explicit Locking](https://www.postgresql.org/docs/18/explicit-locking.html) указывает удержание блокировки до завершения транзакции. Поэтому сильнейшее возражение "NOT VALID само снимает сильную блокировку до VALIDATE в той же транзакции" неверно. Заключение правильно различает корректный SQL и недостаточное указание способа безопасного исполнения. Миграции на БД и настройки конкретных Flyway/Liquibase проектов не запускались.

3. **Дубли навыков.** `plugin-details-review.txt` представляет Component inventory и Projected token cost, явно разделяет always-on и on-invoke и называет токены оценкой. Наличие 36 навыков плагина и 30 совпадающих личных файлов подтверждает дубли в установке и риск повторных описаний. Это не журнал загрузки полных тел всех навыков в один запрос. Заключение не отрицает дубли и обоснованно не превращает inventory в доказательство двойного расхода полного текста.

4. **Refactoring.** Frozen refactoring:17 запрещает назначать численные лимиты "как доказательство плохого кода". Это не запрет соблюдать существующее правило проекта. Текущее `rules/kotlin.md:12` устанавливает конкретный предел вложенности scope-функций; frozen refactoring:25-26 дополнительно советует упрощать цепочки вложенных scope-функций по трудности чтения. Прямого противоречащего повеления не найдено. Возможная неоднозначность признана в заключении, а практическое нарушение моделью не выдается за измеренный факт.

5. **Errors и resilience.** Frozen errors:58-59 прямо упоминает idempotency key и поддержку протокола сервером, а строки 55-57 требуют безопасного повтора, ограничений и обработки отмены. Поэтому утверждение о полном отсутствии ключа в errors не подтверждается. Детали области ключа, соответствия payload и хранения результата там не раскрыты; заключение это признает. Правильность автоматического выбора между навыками еще не измерена.

6. **Остальные существенные границы.** В frozen observability:17-18 оговорка о допустимом основании действительно относится также к credentials/access tokens, поэтому уточнение под безусловное правило пользователя обосновано. [Kotlin conventions](https://kotlinlang.org/docs/coding-conventions.html#choose-good-names) подтверждает обычное именование классов существительными, методов глаголами; заключение не делает это запретом на платформенные исключения. [Oracle JDK 24 migration guide](https://docs.oracle.com/en/java/javase/24/migrate/significant-changes-jdk-24.html) подтверждает освобождение carrier для блокирования в synchronized начиная с JDK 24; отсутствие такого поведения в Java 21 не доказывает, что frozen навык обещает обратное. Данные Codex и расчет p=0.0625 для пяти дискордантных пар не дают основания ни для доказанного общего улучшения, ни для доказанного отсутствия пользы.

Навыки, их установки, правила, AGENTS.md, генератор, validator и runner этим ревью не изменялись. Новых модельных вызовов не было. Текущее содержимое live навыков не рецензировалось; область сравнения - сохраненный frozen текст. Реальное поведение загрузчика, качество маршрутизации, работоспособность UEM под нагрузкой и полнота всех сторонних замечаний не подтверждаются этой проверкой.
