# SOLID в Java и Kotlin

Порядок работы и выбор исправления - методика этого навыка. Метки S1 и далее подтверждают
указанные факты API или рекомендации авторов; они не делают всю методику требованием языка.
Проверь применимость документации к версиям проекта. Примеры ниже адаптированы, если не указано иное.

Добейся понятных обязанностей, совместимых контрактов и управляемых зависимостей в области задачи.
Применяй принципы к конкретным сценариям использования и изменения кода. Наличие интерфейсов,
маленьких классов или Spring DI само по себе не доказывает качество дизайна.

## Разбери контекст

1. Определи режим: проектирование нового кода, ревью или разрешенный рефакторинг. При ревью предложи
   изменения; редактируй, только если задача включает правки. В новом коде сразу выбери подходящую форму.

2. Установи область по заданным файлам или сравнению веток. Для ревью изменений проверь, что выбранный
   diff действительно их содержит; пустой рабочий diff не доказывает отсутствие изменений в ветке.

3. Прочитай ограничения проекта, затронутые типы, их потребителей и реализации. Установи обязательное
   поведение и реальные источники изменений по задаче, контрактам и коду. Не выдумывай владельцев
   требований, будущие реализации и историю изменений. Нужный контекст ищи точечно.

## Проверь применимые принципы

- **SRP, единая ответственность:** какие независимые требования заставляют менять этот модуль?
  Покажи, какие решения сцеплены и кому это мешает. Количество методов или шагов сценария не ответ. [S1]

- **OCP, открытость для расширения:** какой требуемый вариант поведения можно подключить через
  устойчивую границу? Не требуй расширяемости во всех направлениях и не запрещай исправлять код. [S2]

- **LSP, подстановка:** какой корректный для базового контракта клиент ломается при замене реализации?
  Проверь входные требования, результат, ошибки, эффекты и инварианты, а не только сигнатуры. [S3]

- **ISP, разделение интерфейсов:** какие потребители вынуждены зависеть от чужой обязанности?
  Выделяй связные роли по фактическим клиентам, не по правилу "один метод - один интерфейс". [S4]

- **DIP, инверсия зависимостей:** от каких технических деталей зависит политика приложения?
  Проследи импорты, типы в сигнатурах и связи модулей. Передача зависимости через конструктор
  решает способ сборки объектов, но не обязательно направление зависимостей исходного кода. [S4]

## Выбери соразмерное решение

Сравни сохранение текущей формы с минимальным изменением: выделением функции или связной роли,
композицией, функциональным параметром, интерфейсом либо изменением границы модуля.
Для новой абстракции назови потребителя, скрываемую деталь или требуемую вариативность и цену поддержки.
Из определения DIP [S4] не следует требование двух реализаций. Выбор навыка: оставь одну,
если граница нужна уже сейчас, и объясни ее назначение.

Не объявляй автоматически нарушением `when`, `sealed`, `final`, `new`, несколько зависимостей,
`UnsupportedOperationException` или отсутствие интерфейса у класса. Сначала проверь их контракт
и роль. Не вводи `Service`/`ServiceImpl`, generic repository, фабрику, базовый класс или слой только
ради соответствия буквам SOLID. Конкретный стабильный тип тоже может быть уместной зависимостью.

С другой стороны, простота не оправдывает доказанное нарушение контракта или принятой границы.
Если проблема установлена, покажи минимальное исправление и его компромисс. Не своди существенную
связность к вкусу. Если доказательств не хватает, обозначь гипотезу и нужный факт, а не вердикт.

## Сохрани поведение и проверь результат

Перед рефакторингом зафиксируй существенные обещания: API, ошибки, порядок эффектов, атомарность,
владение ресурсами, отмену и время жизни объектов. Проверь применимые риски платформы ниже.
Не превращай структурную правку в изменение бизнес-поведения, публичного API или модели транзакций
без основания в задаче. Не переименовывай соседний код и не перестраивай весь проект по пути.

Проверь именно затронутую границу: контракт клиента на реализациях, сценарий расширения,
компиляцию потребителей, существующие проверки зависимостей модулей или интеграционный сценарий.
Не добавляй тест, который только пересчитывает классы, методы или интерфейсы.
После разрешенных изменений назови выполненные проверки и непроверенные части.

## Дай проверяемый вывод

Для находки укажи место, принцип, факт из кода или требования, конкретный ущерб и минимальное решение.
Добавь цену решения и способ проверки. Объедини находки, если несколько принципов описывают одну
проблему. Отделяй дефект поведения, нарушение принятой архитектурной границы и предложение улучшения.

Не назначай серьезность по названию принципа. Не выдавай числовой "процент SOLID" и не заполняй
отчет искусственными замечаниями по каждой букве. Если обоснованных проблем нет, сохрани текущий
дизайн и кратко объясни значимую границу проверки.

## Платформенные границы и примеры

В Spring при извлечении bean проверь proxy, self-invocation, transaction, qualifiers и lifecycle.
В обычном proxy-режиме вызов @Transactional через this не получает нового перехватывания.
Проверь фактический Kotlin compiler plugin; не открывай все классы ради SOLID.
В coroutine/Android сохрани scope, dispatcher, отмену и момент завершения. Не делай ожидаемую
операцию фоновой ради новой абстракции. Для простого UI-вызова отдельный use case не обязателен. [S5] [S6]

- [Spring Converter](https://github.com/spring-projects/spring-framework/blob/3a91d153165490b0736c9907fda1d8669c6ef3f4/spring-core/src/main/java/org/springframework/core/convert/converter/Converter.java#L38):
  регистрация нового Converter расширяет поведение без переписывания общего convert.
  Изменение регистрационного кода не нарушает OCP само по себе.

- [SendChannel/ReceiveChannel](https://github.com/Kotlin/kotlinx.coroutines/blob/bd2e9a1b90400fb7b2fa4f8731e7d8148799ab73/kotlinx-coroutines-core/common/src/channels/Channel.kt#L23):
  отправляющий клиент принимает SendChannel<Event>; полный Channel объединяет роли и допустим.

- [Okio Source.close](https://github.com/lysine-dev/okio/blob/4ab7768ba238b78834fb9fd76211467165e91fc2/okio/src/commonMain/kotlin/okio/Source.kt#L64):
  повторное закрытие разрешено. Обертка с check(!closed), бросающая на втором close, нарушила бы LSP.

- [JDK List](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/List.html):
  операции изменения необязательны. UnsupportedOperationException при add сам по себе
  не нарушает LSP для читающего клиента; контракт бизнеса с обязательной записью отличается.

- [OkHttp chain](https://github.com/lysine-dev/okhttp/blob/ac3d46c892ef486eca5bd84259dfb9bc8778d909/okhttp/src/commonJvmAndroid/kotlin/okhttp3/internal/http/RealInterceptorChain.kt#L312):
  network interceptor ограничен одним proceed и тем же host/port. Это не универсальное
  ограничение application interceptor, которому разрешен собственный ответ.
