# Модули и зависимости

Назови ответственность и обещания модуля перед перестройкой packages. В ревью предложи правки;
выполняй их по задаче. Не превращай локальный дефект в обязательное внедрение микросервисов.

## Установи реальную границу

Прочитай принятые архитектурные решения, imports, Gradle/Maven dependencies, API и callers.
Раздели package, build module, deployable service и предметную границу: установи, что именно
ограничивает проект. Этот порядок анализа - методика навыка.

## Проверь связность

- **Рекомендация Martin (DIP):** отделяй политику от изменяемых деталей через осмысленную
  границу. Передача зависимости конструктором сама не меняет направление imports. [S1]
- **Контракт Spring Modulith:** модель различает API и internal packages. По умолчанию
  direct subpackages основного application package образуют модули; конфигурация может это менять. [S2]
- **Контракт Spring Modulith:** verify проверяет циклы, доступ к internals и явно заданные
  allowedDependencies. Open modules имеют исключение по доступу к internals. Свяжи замечание
  с реально принятой моделью, не объявляй правило инструмента законом языка. [S2] [S3]
- **Выбор навыка:** не выдавай internal persistence entity через публичную границу, если это
  связывает потребителя с ненужной деталью. Покажи конкретную связь и меньший подходящий контракт.
- **Выбор навыка:** не создавай общий `common` из несвязанных типов только из-за двух callers.
  Если правило имеет владельца, сохрани владельца и явную зависимость.
- **Выбор навыка:** разрывай цикл через изменение ответственности, направление вызова или
  действительно нужный интерфейс. Event bus не используй только для сокрытия цикла imports.
- **Мнение Fowler:** Monolith First описывает аргументы за старт с монолита и признает
  ограниченность опыта автора. Применяй как контекст решения, не как доказанный запрет микросервисов. [S4]
- **Выбор навыка:** оцени стоимость границы: mapping, транзакции, сетевой отказ, совместимость.
  Не добавляй deployable service, если нужен только контролируемый package API.

## Пример Spring Modulith

При уже подключенном Modulith можно проверить модель приложения официальным API. [S3]

~~~java
ApplicationModules.of(Application.class).verify();
~~~

`Application` - класс приложения; импорт ApplicationModules берется из Modulith проекта.
Успех проверяет перечисленные структурные правила, а не правильность предметной области. [S3]
Не устанавливай Modulith только ради исполнения этого примера: используй существующий механизм.

## Проверь

Проверь публичных callers, запрещенные зависимости и существующие module/architecture tests.
Если граница меняет transaction/lifecycle, отдельно проверь этот сценарий.
В находке назови обе стороны зависимости, принятое правило, конкретный ущерб и минимальный переход.
Сохрани простую структуру, если необходимая граница уже понятна и соблюдается.
