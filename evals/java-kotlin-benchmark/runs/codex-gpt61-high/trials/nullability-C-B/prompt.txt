# Nullability и отсутствие значения

Порядок работы и выбор исправления - методика этого навыка. Метки S1 и далее подтверждают
указанные факты API или рекомендации авторов; они не делают всю методику требованием языка.
Проверь применимость документации к версиям проекта. Примеры ниже адаптированы, если не указано иное.

Сделай отсутствие явным и сохрани его предметный смысл. В новом коде выбери контракт;
в ревью покажи нарушающий вход, меняй код только по заданию.

## Определи смысл отсутствия

- Установи, означает ли null нормальное отсутствие, неизвестное значение, непрочитанное поле,
  удаление или ошибку. Не своди разные состояния к одному null для удобства.

- Для обязательного значения обеспечь проверку на границе. Для необязательного используй
  nullable/Optional по языку и существующему API. Не оборачивай Kotlin T? еще одним Optional. [S1] [S2]

- Для нескольких значимых исходов рассмотри явный результат/состояние; не вводи иерархию
  вместо одного простого необязательного значения.

- Не заменяй null на пустую строку, zero, emptyList, default entity или false без согласованной
  семантики. Такая подстановка может превратить отсутствие/ошибку в ложный успех.

- Для PATCH/JSON различай отсутствующее поле, явный null и default, если клиенту это важно.
  Обычный T? не обязан кодировать все три состояния. Проверь реально используемый serializer. [S3]

## Закрой языковую границу

- Установи nullability Java API из аннотаций и контракта. Platform type T! не гарантирует
  non-null: зафиксируй подходящий T? или проверь значение один раз при принятии. [S4]

- Проверь элементы коллекции отдельно от самой коллекции. List<String?>, List<String>?
  и List<String> имеют разные обещания. Java/raw/внешняя десериализация требуют проверки пути. [S1] [S4]

- Не считай присваивание Java-значения в non-null переменную исправлением неверного контракта:
  оно может лишь перенести сбой к месту присваивания. Установи требуемую ошибку или отсутствие. [S4]

- Используй safe call/Elvis/явный if для нужной ветви. Длинная цепочка ?.let может скрыть,
  на каком шаге потеряно значение; раздели ее на смысловые шаги, если это важно клиенту. [S1]

- Для обязательного аргумента используй requireNotNull, для нарушенного состояния checkNotNull
  или предметную ошибку по API. Не используй !! как замену выяснению контракта. [S5]

- У mutable property проверь стабильность между проверкой и использованием. Локальный snapshot
  может решить smart cast и повторное чтение, но не делает составную конкурентную операцию атомарной. [S1] [S6]

- lateinit допустим для реального управляемого lifecycle, но его non-null тип не доказывает
  инициализацию. Не используй его для обхода обязательного constructor dependency. [S7]

- В Java проверь eager/lazy default у Optional. Не вызывай get без доказанного присутствия
  и не превращай пустой Optional в nullable Optional. [S2]

## Примеры

Адаптация [Kotlin Java interop](https://kotlinlang.org/docs/java-interop.html):

~~~kotlin
val name: String? = legacyApi.findName(id)
return name ?: throw NameNotFoundException(id)
~~~

Иллюстративное исключение уместно, только если этот клиент требует наличие имени.
Если отсутствие нормально, сохрани nullable результат; не добавляй exception ради non-null сигнатуры.

[JDK Optional](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/Optional.html)
различает вычисленное значение и supplier:

~~~java
return cached.orElseGet(() -> loadFromStorage(key));
~~~

orElse(loadFromStorage(key)) вызвал бы загрузку при вычислении аргумента даже при наличии cached.
Supplier нужен, когда это различие существенно; константный default не требует lambda. [S2]

## Проверь

Проверь отсутствие, пустое значение, допустимое значение и неверный внешний вход отдельно.
Для JSON/Java interop исполни реальный mapper/вызов: компиляция Kotlin не доказывает внешний контракт.
Проверь, что default не вызывается лишний раз и ошибка не исчезает через mapNotNull/orEmpty.
В находке укажи потерянное состояние или путь сбоя; не запрещай все nullable-типы.
