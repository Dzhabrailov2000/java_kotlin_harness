# Тестирование поведения

Порядок работы и выбор исправления - методика этого навыка. Метки S1 и далее подтверждают
указанные факты API или рекомендации авторов; они не делают всю методику требованием языка.
Проверь применимость документации к версиям проекта. Примеры ниже адаптированы, если не указано иное.

Докажи значимое обещание или воспроизведи дефект минимальной подходящей проверкой.
Не наращивай тесты ради числа и покрытия. При ревью предложи изменения; правь по заданию.

## Выбери проверку

- Установи поведение, которое меняется, и конкретный риск. Для найденного дефекта сначала
  добейся воспроизведения, если это практично; после правки та же проверка должна пройти.

- Проверяй наблюдаемый результат, состояние или существенный эффект. Не привязывай тест
  к private-методу, порядку несвязанных внутренних вызовов и количеству классов.

- Используй unit test для локальных правил. MVC/WebFlux test нужен для binding/filters/advice,
  Spring integration - для proxy/configuration, реальная СУБД - для SQL/constraints/isolation.
  Не заменяй критичный механизм его mock и не называй это проверкой интеграции. [S1] [S2]

- Выбери несколько содержательных границ: допустимую, отклоняемую, отсутствие, конфликт или
  отказ зависимости по изменению. Не перечисляй все мыслимые комбинации и не тестируй stdlib
  вместо собственного контракта. Маленькая локальная rename не требует нового набора тестов.

- Сохрани stack проекта. Выбор этого комплекта для нового JVM backend: JUnit 5, MockK, Testcontainers,
  Kover; не мигрируй существующий Mockito/AssertJ/другой stack ради этого навыка.

## Сделай тест надежным

- Назови сценарий и результат. Используй понятные данные, чтобы ожидаемое было независимо
  от реализации. Не вычисляй expected тем же алгоритмом, который тестируешь.

- Mock используй на реальной границе, если он помогает управлять отказом/эффектом.
  Не строй цепочки mocks для каждой внутренней детали и не делай verify каждого getter.

- Взаимодействие проверяй, когда оно и есть требование: нет списания при отказе, один вызов
  доставки, правильный tenant. Простого assertNotNull недостаточно для содержательного результата.

- Исключение проверяй по нужному типу, cause/полям. Полный текст сообщения фиксируй только
  если это контракт. assertThrows допускает subtype; assertThrowsExactly требует точный класс. [S3]

- Управляй часами, случайностью и scheduler там, где они влияют на результат. Фиксируй zone/locale,
  если они часть сценария; не заставляй тест зависеть от сегодняшнего дня и скорости машины.

- Для async используй сигналы/barrier или bounded ожидание наблюдаемого условия. Не заменяй
  синхронизацию длинным sleep. Для coroutine runTest полезен, но virtual time управляет только
  соответствующим test scheduler и не доказывает отсутствие гонок на разных потоках. [S4]

- Изолируй state/БД/контейнеры и восстанавливай global clock/dispatcher/config. Проверь реальные
  гарантии lifecycle и parallel execution инструмента, прежде чем разделять mutable fixture. [S5]

## Проверь реальную границу

Тест в откатываемой Spring-транзакции может скрыть проблему flush/commit или lifecycle callback.
При нужном сценарии явно достигни соответствующего этапа и проверь результат вне прежнего context.
Не утверждай, что всегда нужно commit: для локального правила достаточно локальной проверки.
Preemptive timeout может исполнить тест на другом thread вне test-managed transaction. [S2]

Контейнер БД должен соответствовать существенной версии/конфигурации проекта и быть готов
при начале теста. H2 не доказывает PostgreSQL DDL/locking. Не включай reuse или общий singleton
так, чтобы результат зависел от оставшихся данных предыдущего запуска. [S5]

## Примеры API

[JUnit Assertions](https://github.com/junit-team/junit-framework/blob/47bbcd1f19ec23fc9b357bd4893fd9d40ef8df89/junit-jupiter-api/src/main/java/org/junit/jupiter/api/Assertions.java#L3165)
дает проверку точного типа, когда это действительно обещание:

~~~kotlin
val failure = assertThrowsExactly<InvalidRecordException> {
    parser.parse(invalidRecord)
}
assertEquals("missing_id", failure.code)
~~~

Тип и parser здесь иллюстративны; expected code берется из заданного API, не из реализации.
Если контракт разрешает subtype, используй более подходящую проверку.

В [coroutines test](https://kotlinlang.org/api/kotlinx.coroutines/kotlinx-coroutines-test/)
delay на реальном Dispatchers.Default не становится виртуальным просто из-за внешнего runTest.
Подмена dispatcher допустима для управления сценарием, но не подменяет проверку реальной гонки. [S4]

## Сообщи результат

Запускай относящиеся к изменению проверки. После успеха расширяй запуск только при новом риске,
изменении или сбое. Не ослабляй assertion и не меняй expected для сокрытия дефекта.
Назови команды, результат и важные непройденные/невыполненные границы. Покрытие и зеленая сборка
не доказывают поведение production. В ревью предложи конкретный недостающий сценарий.
