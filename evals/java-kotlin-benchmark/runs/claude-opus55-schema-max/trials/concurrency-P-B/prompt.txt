# Конкурентность Java и Kotlin

Порядок работы и выбор исправления - методика этого навыка. Метки S1 и далее подтверждают
указанные факты API или рекомендации авторов; они не делают всю методику требованием языка.
Проверь применимость документации к версиям проекта. Примеры ниже адаптированы, если не указано иное.

Сохрани инвариант, время жизни операции и ограниченный расход ресурсов при реальных interleavings.
В новом коде выбери механизм сразу; в ревью обоснуй нарушение, меняй код только по заданию.

## Установи модель исполнения

- Найди владельца состояния, всех читателей/писателей и необходимую область атомарности:
  поток, coroutine, процесс или несколько приложений. Назови конкретную гонку до выбора lock.

- Установи, должен ли вызывающий дождаться результата, кто отменяет работу, кто наблюдает ошибку
  и сколько задач/запросов одновременно выдерживает зависимость. Не создавай фоновую работу молча.

- Различай CPU-работу, блокирующий I/O и suspending API. suspend не превращает JDBC/Files в
  неблокирующий вызов. На event loop и Android main блокирование недопустимо; на обычном
  servlet thread само по себе не ошибка. Учитывай реально используемый стек и dispatcher. [S1] [S2]

## Сохрани общую память

- Предпочти отсутствие общей мутации, неизменяемый снимок или единственного владельца,
  если это упрощает задачу. Иначе защищай целую проверку-и-изменение, а не отдельные поля.

- volatile дает видимость, но не делает counter++ или check-then-act атомарными.
  Thread-safe коллекция не делает произвольную последовательность вызовов транзакцией. [S3]

- Для простой операции используй подходящий atomic API; для связанного состояния - lock,
  Mutex или последовательного владельца. Все конфликтующие пути должны соблюдать протокол. [S3]

- Выбор навыка: не удерживай блокирующий JVM monitor через приостановку. Для сетевого
  вызова внутри критической секции проследи ожидание и зависимость завершения от других locks.
  При нескольких locks установи согласованный порядок получения. [S3]

- Не выдавай mutable-ссылку из-под защиты. Локальный mutex не обеспечивает уникальность в общей БД. [S4] [S3]

- CAS/update-функция может повторяться: вычисляй новое состояние без неповторяемых внешних эффектов. [S5]

## Сохрани scope, нагрузку и отмену

- Используй структурированное время жизни: coroutineScope для дочерних задач запроса, явно
  управляемый scope для работы сервиса. Не используй GlobalScope как обход ожидания или отмены. [S6] [S7]

- async требует наблюдения результата; launch не возвращает бизнес-результат. Обычный child failure
  может отменить siblings до await. supervisorScope выбирай только при независимых задачах
  с определенной обработкой каждой ошибки; CoroutineExceptionHandler не восстанавливает операцию. [S7]

- Ограничивай одновременно исполняемую работу и накопление ожидающих задач. Semaphore вокруг I/O
  не ограничивает миллионы заранее созданных coroutine; для такого входа нужен bounded producer. [S6] [S8]

- Отмена кооперативна. Сохраняй CancellationException; в длинном CPU-цикле проверяй отмену.
  Thread interruption тоже должен дойти до владельца: пробрось InterruptedException либо
  восстанови interrupt flag при переводе в другой контракт. [S9] [S10]

- Таймаут не гарантирует остановку блокирующего API или отсутствие удаленного эффекта.
  Проверь поддержку отмены клиентом. NonCancellable оставляй для необходимого ограниченного cleanup. [S2] [S11] [S7]

- Virtual threads, если доступны в JDK проекта, уменьшают цену ожидания, но не увеличивают емкость
  БД и не устраняют гонки. Не меняй concurrency-модель без измеренной причины и совместимости. [S8]

## Примеры

В [Kotlin concurrency guide](https://kotlinlang.org/docs/shared-mutable-state-and-concurrency.html)
volatile counter++ проигрывает обновления. Для счетчика подходит AtomicInteger.incrementAndGet;
для нескольких связанных полей одной атомарной переменной недостаточно. [S3]

У [StateFlow.update](https://github.com/Kotlin/kotlinx.coroutines/blob/bd2e9a1b90400fb7b2fa4f8731e7d8148799ab73/kotlinx-coroutines-core/common/src/flow/StateFlow.kt#L224)
lambda может быть повторена. Допустимая форма для immutable-состояния:

~~~kotlin
state.update { previous -> previous.copy(attempts = previous.attempts + 1) }
~~~

HTTP-списание внутри этой lambda может повториться. Перенос вызова наружу сам по себе
не дает атомарность между внешним эффектом и state; требуемую связь решай отдельным протоколом. [S5] [S12]

## Проверь и сообщи

Проверь interleaving нарушения, отмену, ошибку дочерней задачи, завершение scope и достижение лимита.
Используй barrier/latch или управляемый scheduler, когда нужна определенная последовательность;
Thread.sleep не доказывает отсутствие гонки. Виртуальное время не проверяет настоящие data races.
В находке покажи доступы, порядок событий, нарушенную гарантию и минимальный механизм.
Не объявляй код thread-safe по одному успешному прогону. [S13]
