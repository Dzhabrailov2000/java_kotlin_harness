# Валидация входа

Проверь заявленные требования в реально вызываемом механизме. Не придумывай ограничения
на имя, знак, длину или пустоту. В ревью предложи правки, редактируй в области задачи.

## Раздели проверки

- **Рекомендация OWASP:** различай синтаксис и предметную допустимость, проверяй их на входной
  границе. Allowlist описывает разрешенный ввод; запрет апострофа не заменяет безопасный SQL. [S1]
- **Выбор навыка:** DTO может представлять сырой ввод; доменный объект - уже принятое значение.
  Размещай проверку там, где она обеспечивает нужную гарантию, без обязательного копирования на все слои.
- **Контракт БД:** уникальность нескольких запросов обеспечивай общим механизмом, например
  UNIQUE. PostgreSQL CHECK принимает true или null, поэтому отдельно реши требование NOT NULL. [S2]

## Проверь Bean Validation и Spring

- **Контракт Bean Validation:** `@Size` допускает null; `@NotNull` запрещает null, но не задает
  непустую строку. Выбирай сочетание под требование, не по имени поля. [S3] [S4]
- **Контракт Bean Validation:** `@Valid` запускает каскадную проверку ассоциации в ходе
  валидации; сама по себе это не constraint обязательности значения. [S5] [S6]
- **Контракт Kotlin:** annotation use-site target определяет field/getter/parameter.
  Default зависит от целей аннотации и настроек компилятора. Для нужного механизма задай
  явный `@field:`/`@get:`/`@param:`, если иначе получается неоднозначность. [S7]
- **Контракт Spring MVC:** путь argument validation и method validation зависит от сигнатуры
  и аннотаций; возможны разные типы ошибок. Учитывай версию и обработай применимые исключения. [S6]
- **Выбор навыка:** проверь наличие provider и фактический вызов через MVC/методный механизм.
  Аннотированный объект, созданный вручную без Validator, не является проверенным объектом. [S5] [S6]
- **Выбор навыка:** межполевое правило выражай на уровне, где видны оба значения; возвращай
  безопасный код/путь поля. Не нормализуй данные скрыто, если это меняет идентичность или требование.

## Пример контракта

Адаптация API Jakarta Validation и Kotlin use-site targets. Для обязательного списка с 1..100
элементами нужны два отдельных ограничения. [S3] [S4] [S7]

~~~kotlin
data class BatchRequest(
    @field:jakarta.validation.constraints.NotNull
    @field:jakarta.validation.constraints.Size(min = 1, max = 100)
    val ids: List<String>?
)
~~~

Эти аннотации не задают допустимость содержимого каждой строки. Добавь element constraint,
только если установлено соответствующее требование и проверена поддержка пути валидации. [S3] [S5]

## Проверь

Прогони допустимую границу, нарушение, null, пустоту и существенное межполевое сочетание через
реальный Validator/MVC. Для уникальности проверь конкурирующие записи на нужной СУБД.
В находке покажи вход, ожидаемый отказ и путь обхода. Не называй отсутствие аннотации дефектом,
если требование уже надежно обеспечено другим механизмом.
