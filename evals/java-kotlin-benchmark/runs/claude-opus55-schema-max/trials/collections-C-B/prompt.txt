# Коллекции, Stream и Sequence

Порядок работы и выбор исправления - методика этого навыка. Метки S1 и далее подтверждают
указанные факты API или рекомендации авторов; они не делают всю методику требованием языка.
Проверь применимость документации к версиям проекта. Примеры ниже адаптированы, если не указано иное.

Сделай преобразование понятным по входу, шагам и результату. В новом коде выбери простую форму;
в ревью покажи конкретный недостаток, меняй код только по заданию.

## Установи семантику

- Определи порядок, дубликаты, пустой вход, null, мутацию и размер данных. List, Set и Map
  не взаимозаменяемы. Не меняй контракт коллекции ради более короткой цепочки. [S1] [S2]

- Выбери ключ по смыслу и стабильному equals/hashCode. Mutable List как ключ может сломать
  lookup; список как ключ допустим при намеренной семантике последовательности и стабильности. [S2]

- Для Map<K, Map<X, List<Y>>> назови уровни. Если это устойчивая предметная структура,
  выдели именованный ключ/результат. Локальный индекс или естественная группировка могут остаться map.
  Не делай Pair/Triple публичным протоколом с неясными first/second/third.

- Установи правило коллизии ключей. Kotlin associateBy оставляет последнее значение;
  Java toMap без merge-функции отвергает duplicate keys. Ни одно поведение не является
  универсально правильным: сохрани, отклони или объедини по требованию. [S3] [S4]

## Выбери читаемое вычисление

- Используй filter/map/flatMap/reduction, когда каждый шаг имеет простой смысл.
  Сложную lambda выдели в содержательно названную функцию или замени ясным циклом.
  Не вводи произвольную квоту методов или длины цепочки вместо оценки читаемости.

- Цикл уместен для раннего выхода, нескольких связанных накоплений и явных эффектов.
  Не превращай его в stream только ради стиля и не усложняй accumulator ради одной строки.

- Не меняй источник во время обхода и не копи результат через внешнюю mutable-переменную
  внутри map/filter/peek. Используй подходящую reduction/collector либо явный цикл. [S5]

- Не помещай обязательные бизнес-эффекты в Java peek/map: optimizer может пропустить этап,
  если результат от него не зависит. Parallel stream добавляет требования к состоянию,
  порядку, ассоциативности и нагрузке; он не является универсальным ускорением. [S5]

- Сохрани encounter order там, где он нужен. findAny и findFirst, unordered и ordered,
  forEach и forEachOrdered имеют разные обещания. Collector не обязан вернуть нужный mutable-тип. [S5] [S4]

- Java Stream ленив и одноразов; терминальная операция запускает обработку, но не закрывает
  I/O-ресурс автоматически. Не возвращай stream из уже закрытого resource scope. [S5] [S6]

- Sequence тоже меняет момент выполнения и ошибок. Некоторые sequences одноразовы;
  не считай их коллекцией-снимком. Для малых/simple pipeline ее overhead может быть лишним. [S7]

- mapNotNull и filterNotNull удаляют данные. Не применяй их, когда null/ошибка должна быть
  объяснена клиенту. orEmpty также меняет смысл отсутствия на пустоту. [S3] [S8]

- Проверь асимптотику: повторный contains в List или запрос БД в lambda может стать дорогим.
  Set/индекс оправдай объемом и требованием; измеряй важный путь, не оптимизируй по виду кода. [S1]

## Примеры открытых API

Адаптация [JDK stream package](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/stream/package-summary.html):

~~~java
int totalWeight = widgets.stream()
    .filter(widget -> widget.color() == RED)
    .mapToInt(Widget::weight)
    .sum();
~~~

Фильтрация, извлечение и сумма читаются отдельно. Допустимость int/переполнения задает контракт;
пример не разрешает заменить точный денежный расчет на int или floating point.

По [Kotlin transformations](https://kotlinlang.org/docs/collection-transformations.html):

~~~kotlin
val byFirstLetter = listOf("apple", "apricot").associateBy { it.first() }
~~~

Останется apricot. Если нужны обе строки, groupBy имеет другую подходящую семантику.
Не добавляй merge с произвольным победителем, чтобы просто убрать исключение дубликата. [S3]

## Проверь

Проверь порядок, коллизии, пустой/отклоняемый вход, эффект мутации и нужную сложность.
Для pipeline с I/O проверь lifetime и фактические вызовы. В ревью укажи потерянные данные,
измененное поведение или конкретную неясность; исправление должно облегчать чтение.
