# Кэш и согласованность

Установи допустимую устарелость и измеримую пользу. В ревью предложи правки;
выполняй их по задаче. Отсутствие кэша само по себе не дефект.

## Определи контракт кэша

Назови источник истины, ключ, scope, допустимую устарелость и поведение при отказе.
Проверь все параметры результата: tenant, права, locale, версию и фильтры, если они влияют на ответ.
Это методика выбора ключа; конкретный состав должен следовать реальному API.

## Проверь механизм

- **Контракт Spring Cache:** default key зависит от аргументов; для одного аргумента используется
  он сам, для нескольких - составной ключ. Если контекст вне аргументов влияет на результат,
  явно включи его или раздели кэши. Сам default не знает предметную область. [S1]
- **Рекомендация OWASP:** проверяй доступ к объекту при запросе. Наличие закэшированного значения
  не дает вызывающему права его читать; не смешивай ответы разных tenant. [S2]
- **Контракт Spring:** self-invocation в proxy-режиме обходит cache advice. `sync = true`
  зависит от поддержки provider и не является общим обещанием межпроцессной блокировки. [S1]
- **Контракт Caffeine:** `cache.get(key, loader)` атомарно вычисляет/вставляет отсутствующее
  значение в этом кэше. Это полезнее отдельного get-then-put при конкурентной загрузке. [S3]
- **Контракт Caffeine:** maximumSize/maximumWeight ограничивают емкость по разным величинам;
  expireAfterWrite и expireAfterAccess отсчитываются от разных событий. Выбери по контракту. [S4]
- **Выбор навыка:** проверь гонку "прочитать старое - записать новое - заполнить кэш старым".
  Удаление ключа не доказывает отсутствие такого исполнения; покажи свой порядок событий.
- **Выбор навыка:** определи, кэшируются ли отсутствие и ошибки. Не превращай сбой загрузки
  в долго живущий "объект не найден". TTL выбери по требованиям, а не по круглому числу.
- **Выбор навыка:** проверь границу commit/invalidation, несколько экземпляров и восстановление
  после потери кэша. Не назначай distributed lock или обязательный Redis локальному справочнику.

## Пример Caffeine

Адаптация официального API. [S3] [S4]

~~~java
Cache<String, String> cache = Caffeine.newBuilder()
    .maximumSize(1_000)
    .expireAfterWrite(Duration.ofMinutes(5))
    .build();
String value = cache.get(key, this::loadValue);
~~~

Размер и TTL иллюстративны. Атомарность относится к этому cache instance, а метод загрузки
должен иметь согласованный контракт ошибок; пример не доказывает свежесть во всех экземплярах. [S3]

## Проверь

Проверь cold/hit/miss, expiry, concurrent load, invalidation и ошибку источника. Для Caffeine
используй управляемый ticker, если проверяешь время: документация поддерживает такую проверку. [S4]
В находке покажи ключ, последовательность событий и устаревший/чужой ответ либо лишнюю нагрузку.
