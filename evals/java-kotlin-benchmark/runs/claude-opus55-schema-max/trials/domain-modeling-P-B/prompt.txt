# Доменные сущности и значения

Порядок работы и выбор исправления - методика этого навыка. Метки S1 и далее подтверждают
указанные факты API или рекомендации авторов; они не делают всю методику требованием языка.
Проверь применимость документации к версиям проекта. Примеры ниже адаптированы, если не указано иное.

Вырази предметный смысл простыми типами и явными операциями. В новом коде выбери форму сразу;
в ревью предложи обоснованное изменение, редактируй только по заданию.

## Выбери понятное представление

- Установи язык предметной области, владельца правил, жизненный цикл и реальные операции.
  Не выводи бизнес-ограничения из названий и не проектируй будущие сценарии без основания.

- Различай entity с устойчивой идентичностью, value object со сравнением по значению,
  транспортный DTO, persistence-представление и временный результат вычисления.
  Их формы могут совпадать, если это не связывает независимые контракты и не раскрывает данные. [S1]

- Используй data class/record для значения, когда generated equality и поверхностная
  неизменяемость подходят. Для entity установи момент появления ID и стабильность equals/hashCode,
  особенно до/после persistence. Не включай изменяемые связи в равенство автоматически. [S2] [S3] [S4]

- Заменяй Map<List<...>, Map<...>> и Pair/Triple с непонятными позициями на именованные
  ключи/значения, когда они имеют устойчивый смысл. Не создавай класс для каждого локального
  промежуточного шага. Обычная map как индекс и локальный Pair при ясном контексте допустимы. [S5] [S1]

- Не используй mutable key: изменение участвующих в equals/hashCode данных ломает lookup.
  Typealias упрощает написание, но не вводит новый тип и не защищает от смешения ID. [S6] [S7]

- Выбирай существующий тип для времени/длительности/валюты, если он выражает контракт.
  День календаря не всегда равен 24 часам. Согласуй единицы, зону, точность и округление с задачей. [S8]

## Сохрани правила и переходы

- Помести локальный инвариант в контролируемое создание или изменение объекта, если объект
  должен всегда его соблюдать. Внешний сырой DTO может временно содержать неверное значение.

- Предпочти предметную операцию набору setters, которые позволяют клиенту обойти переход.
  Несколько boolean с недопустимыми комбинациями могут требовать enum/sealed состояния.
  Не вводи state machine для двух действительно независимых флагов.

- Найди минимальную группу данных, для которой нужно согласованное изменение. Aggregate -
  граница правил и владения, а не копия всех таблиц и связей. Не загружай весь граф ради названия DDD. [S9]

- Межобъектные ограничения и уникальность нескольких процессов требуют общего механизма:
  constraint, транзакции или протокола. require в одном объекте не заменяет его. [S10] [S11]

- Разделяй вычисление решения и внешний эффект там, где это облегчает соблюдение правил.
  Не делай HTTP/JDBC из equals/hashCode, accessors или неочевидного конструктора.

- Сохрани простой transaction script для простого CRUD. Rich domain model, отдельные aggregates,
  repository-порты и обертки над всеми примитивами требуют конкретной пользы. [S12]

## Пример формы данных

Адаптация идеи [Fowler Value Object](https://martinfowler.com/bliki/ValueObject.html):
если ключ означает клиента и день, вырази эти роли вместо списка разнородных значений.

~~~kotlin
data class DailyUsageKey(val customerId: CustomerId, val date: LocalDate)
data class UsageTotal(val requests: Long, val bytes: Long)

val totals: Map<DailyUsageKey, UsageTotal> = emptyMap()
~~~

CustomerId здесь тип проекта, LocalDate - выбранный календарный API. Допустимость отрицательных
значений и политика переполнения требуют предметного контракта; пример их не назначает.
Если операция лишь локально группирует данные по двум известным полям, Pair может быть достаточен.

[Guava Range](https://github.com/google/guava/blob/52d12e4aa2fe8bd1e09811daa4ced7cc99697f45/guava/src/com/google/common/collect/Range.java#L70)
показывает готовый тип с явными границами вместо двух ничем не связанных чисел.
Не переноси ограничения диапазона на другую предметную величину без ее контракта.

## Проверь и сообщи

Проверь допустимое создание, переход, отклонение, равенство и поведение ключа при хранении.
При ORM/JSON-границе проверь именно ее, включая generated ID и внешний формат.
В находке покажи неясный смысл, обход правила или недопустимую комбинацию и более простую форму.
Не называй отсутствие DDD-класса дефектом. Не объединяй unrelated refactor с изменением бизнес-правил.
