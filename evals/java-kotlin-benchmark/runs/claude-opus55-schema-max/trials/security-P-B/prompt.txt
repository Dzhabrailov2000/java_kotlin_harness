# Безопасные границы backend

Порядок работы и выбор исправления - методика этого навыка. Метки S1 и далее подтверждают
указанные факты API или рекомендации авторов; они не делают всю методику требованием языка.
Проверь применимость документации к версиям проекта. Примеры ниже адаптированы, если не указано иное.

Защити конкретные данные и операции на изменяемой границе. В новом коде обеспечь проверку;
в ревью покажи достижимый сценарий, исправляй только в области задания.

## Установи границу доверия

- Назови недоверенный вход, защищаемый объект, действующее лицо и проверяющий компонент.
  Не считай значение доверенным только потому, что оно пришло из очереди или соседнего сервиса.

- Разделяй authentication и authorization. Проверяй право на конкретный объект/действие/tenant,
  а не только наличие сессии или роль без учета контекста. UUID не является проверкой доступа. [S1]

- Получай identity/tenant из доверенного контекста и проверяй право на запрошенный tenant.
  Не принимай ownerId/isAdmin/price/status из DTO как право изменить защищенное поле. [S1] [S2]

- Проверяй реальный путь Spring Security: filter chain, matcher order, method security,
  proxy и настройки. Аннотация без активного механизма не доказывает защиту. [S3] [S4]

- Сохрани явное отклонение неподдерживаемого доступа. Неполученное решение permission-service
  не должно автоматически разрешать операцию. Выбери безопасный ответ согласно контракту. [S1]

## Обрабатывай ввод и вывод

- Значения SQL передавай bind-параметрами. Имена таблиц/колонок и направление сортировки
  не становятся безопасными от placeholder: выбирай их из фиксированного отображения. [S5]

- Внешний URL/file path проверяй по назначению. Для загрузки URL учти redirects, разрешенные
  назначения и доступ к внутренним адресам; один startsWith не задает надежную границу.
  Не предлагай универсальный SSRF-фильтр без учета resolver и сети. [S6]

- Ограничь размеры payload, страниц, файлов, decompression и fan-out, если ввод управляет ими.
  Типизированный DTO не ограничивает автоматически память и стоимость обработки. [S7]

- Используй нужные поля request/response, чтобы не открыть mass assignment и лишние данные.
  Не сериализуй entity целиком, если ее внутренние поля не входят в внешний контракт. [S2]

- Не пиши tokens, passwords, session cookies, чувствительные payload и authorization headers
  в логи/ошибки/URL. Сохрани полезный correlation ID и безопасное описание события. [S8] [S7]

- Не собирай криптографию, JWT verification или password hashing вручную. Используй
  поддерживаемый механизм и проверь конфигурацию: проверка подписи не равна проверке issuer/audience. [S7]

- CORS не заменяет authorization. Не отключай CSRF по одному слову REST: установи, отправляет
  ли браузер credentials автоматически и какие клиенты/способы authentication поддерживаются. [S7] [S9]

## Примеры

Адаптация [OWASP SQL injection guidance](https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html):

~~~java
try (PreparedStatement query = connection.prepareStatement(
        "select id from orders where id = ? and tenant_id = ?")) {
    query.setLong(1, requestedId);
    query.setLong(2, authorizedTenantId);
    // Execute and consume the result inside this scope.
}
~~~

authorizedTenantId должен происходить из уже проверенного контекста, а не просто второго
параметра клиента. Пример показывает binding и область владения; чтение результата также нужно
завершить внутри подходящей области закрытия ResultSet. [S1] [S10]

[Spring method security](https://docs.spring.io/spring-security/reference/servlet/authorization/method-security.html)
требует включения соответствующего механизма. Одна @PreAuthorize без него не доказывает защиту;
неаннотированные методы не становятся автоматически закрытыми от всех вызовов.

## Проверь

Используй изолированные данные и разрешенное окружение. Проверь отказ для чужого ID/tenant,
неверной роли и пропущенного обязательного credential; проверь успешный разрешенный сценарий.
Для SQL проверь, что специальные символы остаются данными, для mapping - что защищенное поле
не принимается из request. Не доказывай authorization только прямым вызовом метода без security path.

В находке назови конкретный доступный путь, недостающую проверку, влияние и минимальное решение.
Не превращай предположение о конфигурации в подтвержденную уязвимость. Не разворачивай полный
аудит инфраструктуры из изменения одного DTO и не проводи атаки на внешние системы для проверки.
