# Проверка внешнего аудита

Проверены выводы [внешнего аудита](/Users/dzabrailovramzan/.local/share/code-reviews/jk-skills-audit-2026-10-06/SUMMARY.md), а не все сервисы UEM. В этой сессии скиллы, правила, установки и AGENTS.md не изменялись. Текущий бенчмарк использует исходный неизменный снимок в [frozen/skills](frozen/skills); номера строк ниже относятся именно к нему. Наличие готовых файлов и успешные ответы на учебных заданиях не означают отсутствие ошибок во всех примерах.

## Подтверждено

- **testing: неверная форма assertThrowsExactly.** Пример в skills/java-kotlin-testing/SKILL.md:75 не компилируется с JUnit 6.0.3. В локальном кэше исходники Assertions.kt у 6.0.3 и 5.13.4 содержат Kotlin assertThrows, но не assertThrowsExactly. Java Assertions.assertThrowsExactly требует Class<T>. Проверка компилятором Kotlin 2.3.21: исходная форма отвергнута, форма assertThrowsExactly(InvalidRecordException::class.java) { ... } скомпилирована. Это проверка API, а не заявление о версии Kotlin в сервисах. Доказательство: junit-audit-check.json. Это моя ошибка в подготовленном примере.
- **sql-migrations: не обозначена граница транзакций.** В SKILL.md:62-64 ADD CHECK NOT VALID и VALIDATE стоят подряд; строка 69 говорит о разделении шагов, но не о commit. Для уменьшения времени сильной блокировки надо завершить транзакцию ADD до сканирования VALIDATE, в том числе проверить фактические границы Flyway/Liquibase. Иначе ADD CHECK удерживает блокировку до завершения общего сканирования. Источники: [ALTER TABLE, Notes](https://www.postgresql.org/docs/18/sql-altertable.html#SQL-ALTERTABLE-NOTES), [Explicit Locking](https://www.postgresql.org/docs/current/explicit-locking.html). SQL синтаксически корректен; проблема в недоговоренном способе безопасного исполнения на работающей таблице.
- **observability: опасная неоднозначность.** Строки 17-18 объединяют credentials, access tokens и прочие чувствительные данные под оговоркой о допустимом основании. Для секретов пользователя действует безусловное скрытие, а оговорка уместна только для разрешенных несекретных данных. Инструкция пользователя имеет приоритет, но текст навыка требует уточнения. Фактическую утечку эта находка не доказывает.
- **naming: пропущено базовое соглашение.** Нет явного правила о существительных для классов и глаголах/глагольных фразах для обычных методов. [Kotlin conventions](https://kotlinlang.org/docs/coding-conventions.html#choose-good-names) формулируют это как обычное соглашение. Оно не должно стать запретом на фабрики, Compose-компоненты, операторы или имена унаследованного API. Отсутствие слова в поиске - повод прочитать текст, а не достаточная проверка всего смысла навыка.
- **Дубли установки есть.** Все 30 файлов существуют в репозитории, ~/.claude/skills и ~/.agents/skills; это обычные каталоги. При первоначальной проверке файлы были идентичны, позднее исходники изменились извне, см. ниже. [Сохраненный вывод claude plugin details jkh](plugin-details-review.txt) показывает 36 навыков, включая эти 30. Дублирование описаний и риск расхождения копий обоснованы. Полная двойная загрузка тел всех навыков в каждый запрос этим не доказана: CLI различает always-on и on-invoke. Он оценивает весь плагин примерно в 2374 always-on токена, а не измеряет удвоение полного тела в реальном запросе.

## Частично подтверждено или завышено

- **concurrency и Java 21.** Ссылка S8 действительно ведет на JDK 25, а различие поведения synchronized важно: освобождение carrier при блокировании в synchronized появилось в JDK 24 ([Oracle migration guide](https://docs.oracle.com/en/java/javase/24/migrate/significant-changes-jdk-24.html)). Нужна явная развилка по версии. Но существующий текст не утверждает, что в Java 21 pinning отсутствует; утверждение, что модель обязательно сделает неверный вывод, не проверено. Цепочку BS и ее поведение под нагрузкой в этой проверке не воспроизводил.
- **refactoring и лимит вложенности.** Фраза "Не назначай лимит ... как доказательство плохого кода" не равна "игнорируй существующий лимит проекта". Прямой запрет соблюдать kotlin.md не найден. Оговорка о сохранении установленных правил сделала бы текст яснее; считать это уже доказанным major-конфликтом слишком сильно.
- **errors и resilience.** Темы повторов пересекаются. Но в errors:58-59 прямо сказано про idempotency key и серверную поддержку. Справедливо, что там нет подробностей области ключа, payload и сохранения результата. Это основание уточнить границы навыков, а не утверждать, что idempotency key отсутствует. Реальный выбор неправильного навыка еще не измерен.
- **Большие описания и одновременная загрузка 3-5 навыков.** Пересечение условий видно по тексту. Сколько навыков действительно выберет модель и каков прирост контекста, без запуска маршрутизации неизвестно. Оценки размера нельзя выдавать за измеренный расход.

## С чем не согласен

- Нельзя обосновать удаление generics, reactive, messaging и других общих тем только отсутствием их в нескольких сервисах UEM. Исходная задача охватывала Java/Kotlin backend, командное ревью и Android; generics пользователь попросил явно. Уместен отдельный профиль UEM, но это другая настройка области применения.
- Уменьшение каждого файла до 4-5 КБ и конкретные слияния не доказаны бенчмарком. Они требуют проверки полноты, выбора навыков и качества на новых задачах. Компактность полезна, произвольная квота байтов не критерий качества.
- Предложение вынести источники в references прямо противоречит запросу пользователя: один файл на навык, с примерами и ссылками внутри. Таблица из 20 open-source примеров в naming также появилась по прямому запросу.
- AGENTS.md не следует автоматически удалять как случайный артефакт: пользователь явно передал его как действующую инструкцию. Корректность каждого импортируемого пути - отдельный вопрос. Инструкции UEM и код сервисов в этой задаче не менялись.

## О бенчмарке

Критика ограничений справедлива: примеры были доступны при разработке, один ответ на условие, оценщик той же модели, маршрутизация не запускалась. Для Codex полный pass 54/60 против 59/60, главный verdict 59/60 против 60/60. Поэтому "главную проблему находит одинаково" неточно буквально, хотя различие мало. Для пяти пар только B и нуля только A двусторонний точный тест Макнемара дает p=0.0625; это не вероятность того, что эффект случаен, и не доказательство отсутствия пользы.

Вывод "набор целиком не годится" сильнее имеющихся данных. Подтвержденные ошибки надо исправить до рекомендации использовать все примеры без проверки. Оснований снести весь набор или сузить его до UEM нет. Текущий Opus-прогон проверяет именно старый снимок; результаты нельзя приписывать будущей исправленной версии.

## Изменение внешнего состояния во время проверки

После первоначальной проверки и завершения 120 ответов обнаружены изменения в семи исходниках: concurrency, errors, naming, observability, refactoring, sql-migrations и testing. Эта сессия их не вносила. На момент повторной сверки личные установленные копии еще совпадали со старым снимком. Поэтому замечания выше относятся к исходной версии, а текущие файлы и установки нужно сверять отдельно. Замороженные тексты и запросы эксперимента сохранились; оценки относятся только к ним. Строгая прежняя проверка совпадения текущих файлов со снимком закономерно не прошла. Режим --snapshot-only проверяет доказательства эксперимента и явно выводит расхождения, не подтверждая качество или синхронизацию новой версии. HTML сохраняет перечень и hashes расхождений на момент сборки.
