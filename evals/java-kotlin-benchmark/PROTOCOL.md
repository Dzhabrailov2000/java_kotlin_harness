# Парное сравнение навыков Java/Kotlin

Зафиксировано до чтения результатов A/B. Изменения навыков после начала серии требуют новой серии.

## Вопрос

Помогает ли содержимое одного выбранного SKILL.md конкретной модели находить ошибку и сохранять
корректное решение в коротком ревью Java/Kotlin? Проверка не измеряет автоматический выбор навыка,
работу Claude Code как агента, написание приложения или качество всех 30 навыков одновременно.

## Дизайн

- 60 сценариев из java-kotlin-suite: 30 с проблемой, 30 корректных, по два на тему.
- A: общая инструкция ревью + сценарий. B: те же данные + один соответствующий SKILL.md целиком.
- Свежий процесс и временный рабочий каталог для каждого ответа; без истории и резюме чата.
- Идентификатор сценария, метка problem/correct и rubric скрыты от испытуемой модели.
- Навык подается явно в текстовом контексте. Это эксперимент с инструкцией, не проверка загрузчика.
- Одинаковая модель, effort, формат ответа, доступ к инструментам и лимит времени в обеих группах.
- Все 120 ответов идут в перемешанном порядке с фиксированным seed 20261006.
- Один ответ на условие: это первичная проверка, не оценка устойчивости по многим повторам.
- Корпус и критерии существовали при разработке навыков. Выборка не является независимым holdout.
- Не подстраивать навыки, критерии или задачи под уже полученные ответы.

## Запуск и изоляция

Предпочтительная среда пользователя - Claude Opus. Отсутствие авторизации блокирует запуск:
не выдавать ошибку CLI за ответ модели и не подменять Opus другой моделью без явной маркировки.
Возможный дополнительный прогон Codex отмечать отдельным названием модели и провайдера.
Ни один такой результат не доказывает эффект на Opus.

Для Codex отключить user config, локальные rules, поиск skills, plugins, memory, hooks,
apps, web, shell и multi-agent; использовать read-only sandbox, пустой рабочий каталог,
project_doc_max_bytes=0. HOME/CODEX_HOME и auth-файлы не переносить. Сохранить фактические CLI-аргументы.
Любой зафиксированный вызов инструмента помечает ответ как непригодный для этого эксперимента.
Клиентское имя модели не считать гарантией конкретного неизменяемого backend snapshot.

## Оценка

Основной показатель: доля сценариев с выполненными must и без нарушений must_not.
Для problem отдельно считать пропущенное требование; для correct - ложное обязательное исправление.
Условное замечание, корректно помеченное как вне доказанного контекста, само по себе не ложный дефект.
Оценивать смысл и достаточность ответа; не требовать точного слова, размера ответа или числа находок.

Критерии не показывать испытуемой модели. Если используется модель-оценщик, передавать ей только
сценарий, rubric и ответы с перемешанными анонимными метками X/Y. Не сообщать группу A/B и навык.
Сохранить объяснения и цитаты. Одна модель в ролях испытуемой и оценщика не является независимым
экспертным ревью; стилистические подсказки могут раскрыть условие даже при скрытых метках.
Автор отдельно проверяет все пары с различающимся исходом и выборку совпадающих исходов.
Ручные поправки сохранять отдельно с причиной; не переписывать исходные оценки.

Публиковать парные исходы: обе прошли, только A, только B, обе не прошли; отдельно неполные пары.
Показывать сырые ответы и критерии, токены input/cached/output, время процесса, ошибки и число
повторных попыток. Денежную стоимость показывать лишь если она возвращена API/CLI. Не пересчитывать
ChatGPT-подписку по тарифам API и не называть неизвестную стоимость нулевой.

## Ограничения и интерпретация

Маленькие авторские примеры допускают потолочный результат у сильной модели. Отсутствие разницы
не доказывает бесполезность навыков; превосходство на этих примерах не доказывает пользу на проекте.
Параллельность, кэширование и задержки сети мешают трактовать wall time как чистую скорость модели.
Библиотечные executable checks из соседнего каталога - отдельное доказательство, не ответы LLM.
Не объединять 30 локальных проверок, 120 A/B-ответов и число оценок в одну цифру «тестов модели».
