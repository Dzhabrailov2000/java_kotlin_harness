# Контракты и инварианты Java/Kotlin

Порядок работы и выбор исправления - методика этого навыка. Метки S1 и далее подтверждают
указанные факты API или рекомендации авторов; они не делают всю методику требованием языка.
Проверь применимость документации к версиям проекта. Примеры ниже адаптированы, если не указано иное.

Установи, что тип или операция обещает потребителю, и обеспечь это обещание на значимых путях.
Под контрактом здесь понимается поведение API и состояния объектов. Kotlin `contracts {}` описывает
сведения для компилятора и сам по себе не проверяет бизнес-ограничения во время выполнения. [S1]

## Установи область и основание

1. Определи режим: проектирование, ревью или разрешенная правка. При ревью дай рекомендации;
   меняй код, только если задача включает изменения. Ограничь анализ затронутыми типами и клиентами.

2. Прочитай требования, публичный контракт, связанные тесты и реализацию. Отдели обязательное
   поведение от фактического. Противоречие между ними - предмет проверки, а не повод объявить
   текущую реализацию эталоном. Не придумывай ограничения на знак, пустоту, формат и уникальность.

3. Если правило не установлено, обозначь недостающий факт и условные варианты. Не усиливай
   предусловие публичного API и не меняй смысл ошибок под видом улучшения валидации.

## Сформулируй существенные гарантии [S2]

Для затронутой операции установи:

- Какие входы и исходные состояния допустимы: границы, единицы, null, пустота, порядок вызовов.

- Что получает клиент при успехе: значение, наблюдаемое состояние, выполненные эффекты и ресурс,
  если операция передает владение им. Проверь точное условие успеха, а не только тип результата.

- Как различаются отсутствие результата, ошибочный ввод и сбой; какие изменения возможны при
  исключении, отмене или таймауте. Отказ сам по себе не доказывает отсутствие эффекта. [S3]

- Что должно оставаться истинным на границах наблюдения объекта; относится ли ограничение к
  одному экземпляру, нескольким объектам или данным, доступным нескольким процессам.

Не превращай этот список в обязательный отчет о неприменимых свойствах. Для простой функции
достаточно нескольких конкретных обещаний. Для неясного контракта сначала установи его смысл.

## Проследи сохранение контракта

Найди относящиеся к задаче пути создания и изменения: constructor/factory/builder, setter,
`copy`, восстановление из внешнего представления и выдачу ссылок на внутреннее состояние.
Проверь, где недостоверные данные становятся доверенным значением и можно ли обойти эту границу
обычным поддерживаемым вызовом. Не считай аннотацию или закрытый конструктор полным доказательством.

Проверь только значимые механизмы:

- Тип действительно различает сущности и допустимые состояния, а не только переименовывает примитив.

- Изменяемые ссылки не позволяют нарушить обещание снимка или инвариант после валидации.

- Равенство, хеширование и порядок согласованы с ролью значения и использованием в коллекциях.

- Отклонение входа сохраняет именно обещанное состояние; порядок проверки и мутации это обеспечивает.

- Проверка и изменение общего состояния защищены как одна операция там, где нужна атомарность.
  Повторяемая функция обновления не выполняет неповторяемый внешний эффект. [S4] [S5]

Как показывает пример HttpUrl.Builder ниже, промежуточный builder может быть неполным.
Выбор навыка: проверь границу выдачи готового
объекта и возможность наблюдения промежуточного состояния, прежде чем требовать запретить его.

## Выбери минимальное обеспечение и проверь

Сравни проверку аргумента, фабрику, отдельный тип, ограничение мутации, защитную копию и механизм
атомарности по конкретной гарантии. Не требуй обертки для каждого примитива, rich domain model
для каждого CRUD-сценария, одинаковой валидации на всех слоях или DSL контрактов в каждой функции.
Проверка на внешней границе и защита инварианта внутри могут решать разные задачи.

При правках сохрани разрешенные входы, существенные ошибки, формат данных и порядок эффектов,
кроме явно исправляемого нарушения. Проверь допустимую границу, отклоняемый случай и наблюдаемое
состояние после него. Для конкуренции, сериализации или Spring-вызова используй соответствующий
путь исполнения; прямой вызов конструктора не доказывает корректность остальных путей.

Для находки укажи место, источник обещания, конкретный нарушающий сценарий, минимальное решение
и способ проверки. Различай дефект, неизвестное требование и необязательное улучшение модели.
Если контракт соблюден, сохрани решение. После правок назови выполненные и невыполненные проверки;
не выдавай список предлагаемых тестов за результат их запуска.

## Границы JVM и Kotlin

Kotlin typealias не создает отдельный тип. Value class различает типы, но не выводит проверки
из имени и может требовать boxing. val и List не гарантируют глубокую неизменяемость.
Data class copy поверхностный; поля тела класса не входят в автоматически выведенное равенство.
Java record тоже не замораживает компоненты. Копия контейнера не копирует mutable-элементы.
Не требуй глубокой копии неизменяемых String или обязательной новой аллокации контейнера. [S6] [S7] [S8] [S9] [S10]

Java assert может быть отключен и не заменяет обязательную проверку публичного аргумента.
Аннотация требует действующего валидатора: прямой вызов объекта не доказывает MVC validation.
Проверь поддерживаемый путь десериализации/ORM. Kotlin copy не обязательно обходит init;
стандартная Java десериализация record вызывает canonical constructor. [S11] [S12] [S8] [S9]

BigDecimal.equals различает 2.0 и 2.00, compareTo - нет. Установи значимость scale; не округляй
значение произвольно. При числовом равенстве обеспечь согласованный hashCode.
Локальный lock не защищает несколько процессов, @Transactional не доказывает нужную изоляцию.
Таймаут, отмена и rollback БД не гарантируют откат обычного HTTP-эффекта. [S13] [S14] [S15] [S3]

## Примеры из открытых API

- [CP01. Guava Range: пустое не обязательно недопустимо](https://github.com/google/guava/blob/52d12e4aa2fe8bd1e09811daa4ced7cc99697f45/guava/src/com/google/common/collect/Range.java#L70): Range.closedOpen(5, 5) пуст и допустим; closed(5, 5) содержит точку, open(5, 5) недопустим. Универсальное start < end неверно.

- [CP02. OkHttp HttpUrl: проверки на разных стадиях](https://github.com/lysine-dev/okhttp/blob/ac3d46c892ef486eca5bd84259dfb9bc8778d909/okhttp/src/commonJvmAndroid/kotlin/okhttp3/HttpUrl.kt#L997): Builder.port проверяет 1..65535 до присваивания; отказ этого метода сохраняет прежний port. build отдельно требует scheme/host.

- [CP03. Guava ImmutableList: обещание состояния, не новой ссылки](https://github.com/google/guava/blob/52d12e4aa2fe8bd1e09811daa4ced7cc99697f45/guava/src/com/google/common/collect/ImmutableList.java#L248): copyOf может переиспользовать безопасный immutable-контейнер; элементы не клонируются. Новая ссылка не обещана.

- [CP04. Okio: состояние после неудачного чтения](https://github.com/lysine-dev/okio/blob/4ab7768ba238b78834fb9fd76211467165e91fc2/okio/src/commonMain/kotlin/okio/BufferedSource.kt#L430): readUtf8LineStrict(limit) не отбрасывает байты при неудачном поиске. Это не гарантия отсутствия чтения из нижележащего потока и любых I/O-эффектов.

- [CP05. OkHttp Call: IOException не доказывает отсутствие эффекта](https://github.com/lysine-dev/okhttp/blob/ac3d46c892ef486eca5bd84259dfb9bc8778d909/okhttp/src/commonJvmAndroid/kotlin/okhttp3/Call.kt#L46): IOException возможен после принятия запроса сервером. Отказ не доказывает отсутствие внешнего эффекта.

- [CP06. StateFlow: атомарная запись и повторяемое вычисление](https://github.com/Kotlin/kotlinx.coroutines/blob/bd2e9a1b90400fb7b2fa4f8731e7d8148799ab73/kotlinx-coroutines-core/common/src/flow/StateFlow.kt#L224): StateFlow.update может вычислить lambda повторно. Атомарность значения не означает однократный внешний вызов; мутация общего значения также мешает equality-based публикации.

- [CP07. kotlinx-datetime: знак зависит от смысла величины](https://github.com/Kotlin/kotlinx-datetime/blob/0a95c206ad61f5d6c47455cf76cb15d697fe2616/core/common/src/DateTimePeriod.kt#L19): DateTimePeriod допускает отрицательные и разнонаправленные компоненты. Знак сдвига не ограничивается по одному слову Period.

- [CP08. Kotlin contracts DSL: описание не исполняет проверку](https://github.com/JetBrains/kotlin/blob/b3fa20c6b7db51a41baed91c531a65aa94498b18/libraries/stdlib/src/kotlin/contracts/ContractBuilder.kt#L227): returns() implies (value != null) не проверяет аргумент. Тело функции должно обеспечить обещание компилятору.
