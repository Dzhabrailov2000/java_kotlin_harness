# Отказоустойчивые вызовы

Ограничи время и нагрузку, сохрани правильность эффекта. В ревью предложи правки;
выполняй их по задаче. Не добавляй все механизмы сразу к каждому вызову.

## Установи сценарий отказа

Найди caller deadline, настройки клиента/SDK, очередь, лимиты зависимости и требование к результату.
Запиши владельца retry и состояние после неизвестного ответа. Отдели допустимое устаревшее
значение от ложного успеха. Этот порядок анализа - методика навыка.

## Выбери механизм по задаче

- **Контракт HTTP:** автоматический повтор неидемпотентного запроса требует основания знать,
  что семантика идемпотентна либо исходный запрос не был применен. Одного IOException недостаточно. [S1] [S2]
- **Контракт OkHttp:** IOException возможен после принятия запроса сервером. Сохрани исход
  "неизвестно", если подтвердить эффект невозможно; не изображай гарантированный rollback. [S2]
- **Рекомендация AWS:** повторяй подходящие временные отказы с ограничением попыток/времени,
  backoff и jitter. Учитывай встроенные повторы и их умножение на нескольких слоях. [S3]
- **Рекомендация AWS:** не повторяй без изменения условий отказ permission/configuration;
  не пиши собственный retry engine, когда существующий механизм покрывает нужный контракт. [S3]
- **Контракт HTTP:** Retry-After может содержать delay-seconds или HTTP-date. Учти заголовок
  в рамках своего deadline; он не разрешает повтор небезопасной операции. [S4]
- **Контракт Resilience4j:** размер sliding window CircuitBreaker не ограничивает число
  одновременных вызовов. Для этого нужен соответствующий bulkhead/лимит; breaker решает иную задачу. [S5]
- **Выбор навыка:** установи общий бюджет, timeout попытки и отмену ожидания. Проверь, завершает
  ли отмена реальное I/O; поддержка interruption зависит от вызываемого API. [S6]
- **Выбор навыка:** для idempotency-протокола определи ключ, область клиента, проверку payload,
  хранение результата и срок дедупликации. Случайный новый ключ на каждую попытку не выражает повтор
  той же операции. Обоснование - требуемая семантика повторного эффекта, не магия заголовка. [S1]

## Пример из Resilience4j

В документации: CLOSED breaker со sliding window 15 может разрешить 20 одновременных вызовов.
Окно хранит статистику, а не 15 разрешений на исполнение. [S5]

~~~text
Требование: одновременно максимум 8 вызовов к зависимости.
Проверка: отдельный лимит in-flight + ограниченная очередь/отказ.
CircuitBreaker: добавь только при отдельной задаче отсечения отказов.
~~~

Число 8 иллюстративное; выбирай лимит из емкости и требований, не копируй его в production.

## Проверь

Проверь временный и постоянный отказ, потерю ответа после эффекта, отмену во время backoff,
исчерпание бюджета и лимита. Считай фактические попытки и эффекты отдельно. Покажи настройки
реального клиента; аннотация retry без проверки пути исполнения не завершает работу.
