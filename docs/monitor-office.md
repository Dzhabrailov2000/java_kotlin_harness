# Офис конвейера в мониторе прогресса

Панель «Офис конвейера» на странице `scripts/run_progress.html` рисует комнату, мебель и трех
персонажей оригинальным движком [Pixel Agents](https://github.com/pixel-agents-hq/pixel-agents)
(MIT, Copyright (c) 2026 Pablo De Lucca; спрайты персонажей восходят к пакету MetroCity, см. README
апстрима). Движок и ассеты скопированы байт в байт из закрепленной ревизии, собраны один раз и лежат
в репозитории готовыми: обычный запуск монитора остается запуском Python без Node.

```
python3 scripts/run_progress.py serve --progress-dir DIR
```

## Главный экран: офис, цикл и одна кнопка подробностей

Закрытый экран по умолчанию помещается в 1400x900, 1440x900 и 1920x1080 без обрезки и без
принудительного `overflow: hidden`, а на 390 px остается читаемым при обычной вертикальной
прокрутке. На нем ровно четыре вещи:

- **Компактная шапка в одну строку:** название задачи, `run`, попытка, время обновления, текущий
  этап, состояние связи и кнопка «Подробности». Заголовок - это опознание задачи, а не пересказ
  запроса: длинный запрос сокращается многоточием, а его полный текст с авторством остается
  сообщением пользователя в разделе «Разговор» и в записях персонажа «Пользователь».
- **Офис** как главный визуальный элемент и три кнопки участников под ним.
- **Цикл** из пяти узлов основного пути: Код - Тесты - Ревью - Разбор - Решение, с дугой возврата
  «Исправления» и строкой состояния под ней. Verify и handoff показываются отдельными фишками
  только при собственных записях этих фаз.
- **Короткий кредит** внизу: движок и лицензия. Команда консольного журнала (`tail -f`), справка
  «как читать страницу» и команды менеджера лежат в разделе «Журнал» внутри подробностей.

Рядов карточек с метриками, полной истории этапов, сырого разговора и диагностики на главном
экране нет: все это доступно по кнопке «Подробности» и никуда не удалено.

### Что говорит цикл и чего он не говорит

Топология нарисована статически и сама по себе ничего не утверждает. Состояния берутся из тех же
`officeEntry`/`officeObserved`, что и сцена:

| Что видно | Что это значит |
|---|---|
| `не начат`, серый | записей этой фазы в наблюдаемой попытке нет |
| `запускается: ШАГ`, пунктир | запуск записан, ни одной записи CLI еще не наблюдалось |
| `идет` (или `N вызовов`), желтый с пульсацией | наблюдаемый вызов CLI текущей попытки, который еще идет |
| `история: ШАГ` / `история, тишина` | записи CLI импортированы: они описывают прошлый запуск, а не текущую работу |
| `тишина ...`, точечный | наблюдений нет дольше порога: состояние не подтверждено |
| `CLI завершил`, синий | ход CLI закончился; приемкой задачи это не является |
| `RETRY` / `VERIFY` / `COMPLETE`, `запись менеджера` | записанное событие менеджера, а не наблюдаемая работа |
| `нет связи` | данные не обновляются; последнее известное состояние остается видимым, но не подтверждено |

Каждый запрос к своему же серверу ограничен собственным сроком (5 с на весь ответ, вместе с телом).
Без него запрос, оставшийся без ответа, не завершался бы ни успехом, ни ошибкой: шапка продолжала бы
показывать связь по прошлому удачному опросу, а следующий опрос, который планируется только по
завершении текущего, не был бы поставлен вовсе. По истечении срока запрос отменяется, страница
показывает `нет связи` и возвращается к обычным повторам с задержкой. Ответ, пришедший после этого,
в данные не попадает: наблюдение уже признано несостоявшимся, и уже прочитанные записи остаются
последним известным, а не подтвержденной текущей работой.

Дуга возврата - тоже запись, а не оформление: она активна только по записанному решению RETRY
текущей попытки и становится пройденной только по RETRY более ранней попытки. Один лишь номер
попытки возврата не доказывает, и подпись остается нейтральной «Исправления». Наблюдаемая попытка
при этом всегда названа в строке состояния.

Строка состояния цикла собирает всю наблюдаемую работу, включая условные verify и handoff. Записанное
решение по задаче ее не вытесняет: идущая передача и решение COMPLETE показываются как два разных
факта в одной строке.

### Подробности по требованию

Кнопка «Подробности» (а также выбор персонажа или узла цикла) открывает один инспектор с разделами
«Разговор», «Сессии», «Метрики» и «Журнал». Выбор персонажа или фазы открывает контекст этой записи
над разделами; одновременно показывается один контекст, а не два. Инспектор закрывается кнопкой или
Escape, фокус возвращается на то, откуда его открыли, и опрос закрытый инспектор не воскрешает.

Фильтры, разворачивание сообщений, режим «следить за концом» и позиция чтения переживают закрытие:
позиция разговора снимается, пока раздел еще виден (при уходе с него и при закрытии из него), поэтому
уход через другой раздел не заменяет ее нулевой геометрией скрытого блока.

## Что это, а что нет

Встроен только офисный движок: комната, мебель, персонажи, анимация и попадание курсора. Редактор
планировки, настройки, терминал, обнаружение сессий и хуки апстрима не переносились и не работают.
Канвас - это визуальный слой над теми же данными, которые показывает остальная страница; ни одного
собственного источника состояния у панели нет.

## Кто есть кто

| Персонаж | Роль | Что показывает |
|---|---|---|
| Пользователь | человек | Записи с `role=user`, даже если запись создал менеджер (`source=manager`). Человек не наблюдаемый процесс: работа за него не анимируется. |
| Codex | менеджер | Записи и решения менеджера. Наблюдаемое независимое ревью показывается за этим столом только с явной подписью `независимое ревью · отдельная сессия`. |
| Claude | исполнитель | Актуальный вызов Claude: запрошенный профиль и наблюдаемая модель показаны раздельно, инструмент - по незавершенному вызову. |

Состояния берутся из существующих редьюсеров страницы (`summarize`, `summarizeTrace`, `stepState`).
Анимация работы включается только для наблюдаемого «идет сейчас». Тишина, ожидание повтора API,
импорт старого журнала, завершенный CLI и потеря связи работой не считаются; успешный выход CLI не
является приемкой - ее записывает только менеджер. Отсутствие записей родительского менеджера
остается «неизвестно», а не «работает».

Сцена различает запуск и работу отдельно от остальной страницы (`officeEntry`, `officeObserved`):

- `run/started` и `cli_started` пишет лаунчер до старта процесса, поэтому до первой записи самого
  CLI (`init`, вызовы инструментов, `capture_started` с сессией, поток Codex, сообщения модели,
  `api_retry`) персонаж показан как `запускается`, без рабочей анимации. После порога тишины это
  становится `запуск не подтвержден`, а не работой.
- Завершенный ход (`cli_result`) без `cli_exit` и `result` - это `ход завершен, процесс
  закрывается`: модель уже не работает. Без записи выхода дольше порога тишины состояние
  становится неподтвержденным, а не бессрочно рабочим.

Остальная страница (этапы, карточки, «Вызовы LLM») читает те же записи прежним `stepState`:
офис не заводит своего источника состояния и не меняет семантику существующих представлений.

Выбор персонажа - клик по фигуре на канвасе или нативная кнопка под сценой (клавиатура работает как
обычно). Выбор открывает записи этого участника с сохранением автора, вида, модели, шага, попытки и
пометок об импорте и усечении; полный текст, фильтры и история остаются в разделе «Разговор».
Переключатель «движение» и системная настройка «уменьшить движение» останавливают симуляцию, при
этом состояния продолжают обновляться и перерисовываться. Выбор и фокус переживают перерисовку.

## Как это собрано

```
monitor/pixel-office/
  vendor/                 копии оригинальных исходников и ассетов (не редактировать)
  vendor-manifest.json    репозиторий, коммит, sha256 и размер каждого файла vendor/
  src/office.ts           адаптер: монтирование, снимок состояния, подписи, выбор, масштаб
  src/assets-build.ts     сборочный декодер ассетов (только Node, только на этапе сборки)
  build.mjs               проверка манифеста, сборка, проверка графа модулей, запись провенанса
  dist/office.js          собранный бандл, который отдает сервер
  dist/assets.json        предекодированные спрайты и планировка
  dist/build-manifest.json входы и выходы сборки с хешами
```

Пересборка нужна только при изменении адаптера или обновлении апстрима:

```
cd monitor/pixel-office
npm ci --ignore-scripts      # esbuild 0.28.1 и pngjs 7.0.0, пины из апстрима; postinstall не запускается
npm run build                # печатает sha256 и значение integrity для страницы
```

Сборка отказывается работать, если хоть один файл `vendor/` разошелся с манифестом или если
декодер ассетов что-то пропустил: неполный набор спрайтов не считается успехом. Чистая пересборка
дает те же байты. `node_modules/` и временный `build/` не версионируются.

После пересборки в `scripts/run_progress.html` нужно обновить `integrity` у тега
`<script src="/pixel-agents/office.js">` значением, которое напечатала сборка;
`tests/test_pixel_office.py` не даст этому разойтись.

## Хостинг и политика безопасности

`ProgressServer` читает страницу и оба файла сцены один раз при старте и отдает их по двум точным
путям: `/pixel-agents/office.js` (`application/javascript`) и `/pixel-agents/assets.json`
(`application/json`). Общего файлового сервера нет, путь запроса ни с каким каталогом не
склеивается, остальные пути под этим префиксом дают 404. Если сборки нет, маршрут отвечает 503, а
страница показывает видимую ошибку вместо пустого «работающего» офиса.

CSP разрешает ровно один внешний скрипт - по sha256 его собственных байтов, и страница несет тот же
хеш в `integrity`. Инлайновые хеши скрипта и стиля, `img-src 'none'`, `connect-src 'self'`,
`default-src 'none'` и запрет фреймов сохранены; `unsafe-inline`, `unsafe-eval`, внешние адреса и
новые эндпоинты не добавлялись. Канвас не требует ни изображений, ни фреймов, ни сети: спрайты
приходят готовыми в JSON и рисуются в обычный 2d-контекст.

## Проверки

```
python3 -m unittest tests.test_pixel_office tests.test_run_progress tests.test_run_progress_browser
python3 -m unittest tests.test_monitor_minimal
```

`tests/test_monitor_minimal.py` проверяет главный экран: отображение записей в узлы цикла (запуск,
наблюдаемый вызов, параллельные вызовы, импорт, тишина, потеря связи, запись менеджера, дуга
возврата, условные фазы) на заглушке DOM и закрытый экран в headless Chrome - вписывание в
1400x900, 1440x900, 1920x1080, компактность шапки и подписи цикла на 390 px, работу инспектора,
клавиатуру, паузу движения и потерю связи.

`tests/test_pixel_office.py` проверяет провенанс сборки (хеши vendor и dist, пин на странице, состав
графа модулей), вывод состояний по реальным ответам API на заглушке DOM (в том числе запуск без
наблюдений CLI и завершенный ход ревью) и живую сцену в headless Chrome: рендер оригинальных
спрайтов, выбор мышью и клавиатурой, сохранение фокуса, остановку симуляции при reduced motion,
ширины 390 и 1400 px без перекрытия подписей и потерю связи. Потерянный поток проверяется по
наблюдению самой страницы: сцена читается только после того, как страница сказала «нет связи», а не
через фиксированную паузу, которая сама по себе не доказывает, что хоть один опрос не удался.

Сроки запросов проверяются в `tests/test_run_progress.py` на управляемой сети: обычный ответ, отказ,
запрос без заголовков, недочитанное тело, ответ после истечения срока и возврат к опросу после сбоя.
Заглушка отменяет запрос так же, как это делает браузер, и считает оставшиеся таймеры, поэтому
забытый срок виден как утечка, а не как успешная проверка.
