# Офис конвейера

Монитор показывает конвейер оригинальным интерфейсом
[Pixel Agents 1.4.1](https://github.com/pixel-agents-hq/pixel-agents) (MIT, Copyright (c) 2026
Pablo De Lucca; спрайты персонажей восходят к пакету MetroCity, см. README апстрима). Это не
похожая на него панель: комната, рендерер, редактор планировки, шрифт, оверлеи и вся композиция -
собранное из закрепленных исходников оригинальное приложение. Локальными остаются только адаптер,
который кормит его нашим журналом, и девять именованных патчей, перечисленных ниже.

```
python3 scripts/run_progress.py serve --progress-dir DIR
```

Команда печатает один рабочий URL. По нему открывается офис; журнал доступен по кнопке `Journal`
внизу слева и по адресу `<URL>/details`.

## Что на экране

Экран - это офис и ничего больше: комната, три персонажа, зум, `Layout`, `Settings`, `Journal` и
индикатор версии. Карточек с метриками, графа этапов, таблиц и сырого разговора на нем нет: все это
живет в журнале.

Над каждым персонажем - нативная панель оригинала. Обычная подпись компактна: имя роли и короткая
форма состояния, чтобы подписи соседних столов не закрывали друг друга. Наведение или выбор
персонажа раскрывает ту же панель полностью: роль, что наблюдается сейчас и происхождение этого
наблюдения (попытка, шаг, при параллельных вызовах их число). Точный текст всех наблюдений в любом
случае лежит в журнале.

| Персонаж | Роль | Что показывает |
|---|---|---|
| Пользователь | человек, автор задачи | Зарегистрирован ли запрос пользователя. Человек - не наблюдаемый процесс: анимации работы у него нет никогда. |
| Codex | менеджер | Записи и решения менеджера и результаты приемочных расписок. Наблюдаемая независимая проверка подписывается отдельно: `Codex · независимая проверка`. |
| Claude | исполнитель | Текущий вызов Claude; при передаче отчета роль подписана как `Claude · передача отчета`. |

Три персонажа - это три роли, а не три работающие модели. Одна роль может объединять несколько
реальных сессий; какие именно, с моделями, попытками и шагами, показывает журнал.

### Состояния и что они значат

Анимация работы включается только на наблюдаемом вызове CLI. Все остальное - видимо не работа, и
ни одно состояние не рисует зеленую галочку завершенного хода.

| Состояние | Что это значит |
|---|---|
| `human` | человек; монитор его работу не наблюдает |
| `idle` | наблюдений работы нет: запуск запрошен, ход завершен, отчет передан, записан результат |
| `working` | наблюдаемый вызов инструмента или идущий ход CLI, с именем инструмента |
| `waiting` | наблюдаемая пауза: повтор запроса к API после ошибки |
| `unknown` | записей об этой роли нет |
| `error` | наблюдаемый отказ: таймаут, прерывание, ненулевой код выхода, незавершенная работа |
| `stale` | последнее наблюдение старше двух минут, а завершения не записано |
| `offline` | связь с монитором или его источник потеряны: ни одно утверждение об активности не свежее |

Запуск исполнителя и его работа - разные вещи: `run/started` пишет лаунчер до старта процесса,
поэтому до первой записи самого CLI персонаж стоит с подписью «запуск запрошен, активность не
наблюдалась». Успешный выход CLI приемкой не является; COMPLETE записывает только менеджер, и
только по проверенной расписке завершения.

Импортированные записи (`source=import`) - история: они не анимируют персонажа и не становятся
живым ожиданием API.

У одной роли может быть записано несколько вызовов. На столе показывается один, и выбирает его не
порядок записей: сначала наблюдаемая прямо сейчас работа, потом более поздняя попытка, потом вызов
с незакрытым исходом, потом более позднее наблюдение. Поэтому завершенный ход одной сессии не
гасит свежую работу соседней, пока ее процесс еще не вышел, а брошенный вызов старой попытки не
закрывает собой отказ новой. Число параллельных сессий в подписи - это вызовы, которые сейчас идут:
не вышедшие и не замолчавшие. Все остальные наблюдения остаются в журнале и в деталях.

Записанный факт (расписка, решение, зарегистрированный разбор) становится подписью, только пока он
новее всего наблюдавшегося у этой роли - по попытке и по времени, а не только новее того вызова,
который сейчас на столе. Старый PASS не заменяет собой отказ или тишину, наблюдавшиеся после него.

### Семантика проверок и ревью

Результаты попадают в офис автоматически, но только из запечатанных расписок:

- `run_acceptance.py check --progress-dir DIR` после запечатывания расписки пишет свой результат:
  PASS, FAIL или UNVERIFIED. Таймаут, прерывание, несостоявшийся запуск и дерево, изменившееся под
  командой, - это UNVERIFIED: о коде они не говорят ничего. Запись несет id расписки, дайджест
  дерева-кандидата и число объявленных в плане проверок.
- Агрегат «проверки: N PASS из M» считается внутри одной попытки и одного дерева-кандидата.
  Пересобранное дерево начинает свой агрегат: прежний PASS остается историей.
- `run_codex_review.py --acceptance-dir ...` после локальной валидации ответа пишет вердикт.
  Проверенный FAIL остается FAIL, хотя и сам процесс ревью, и его лаунчер выходят с кодом 0.
  Невалидированное ревью - UNVERIFIED, что бы ни утверждал его текст.
- Зарегистрированная обратная связь разбора (`run_trace.py register --phase triage --kind feedback`)
  читается как «обратная связь зарегистрирована». Состав и число замечаний остаются неизвестными:
  прозу монитор не разбирает.
- COMPLETE - по-прежнему явное событие менеджера с расписки завершения. Ни процесс, ни расписка,
  ни наблюдение сами по себе его не создают.

Отказ наблюдения не влияет ни на один вердикт: если адаптер не может прочитать источник, персонажи
уходят в `offline`, а расписки и записи остаются какими были.

## Журнал

Кнопка `Journal` открывает `<URL>/details` в новой вкладке - ту же читаемую сторону, что и раньше,
без второго офиса и без графа этапов: разделы «Разговор», «Сессии», «Метрики» и «Журнал». Там
остаются точные промпты и публичные ответы, ссылки на зарегистрированные артефакты, попытки,
происхождение записей, использование токенов, состав обвязки и контекст сессий. Фильтры, разворот
сообщений, режим «следить за концом» и позиция чтения ведут себя как прежде.

Занятость контекста монитор не выдумывает: суммарный расход токенов - это расход, а не занятое
окно, поэтому нативный указатель контекста в офисе не показывается никогда.

## Настройки офиса

Работают нативные `Layout` (редактор планировки, области, мебель, ковры, питомцы), `Settings`
(звук, всегда показывать подписи, области, отладочный вид, экспорт и импорт планировки) и зум.
Планировка, места персонажей, области и настройки хранятся в собственном локальном каталоге
монитора:

```
${XDG_STATE_HOME:-~/.local/state}/java-kotlin-harness/pixel-office/
```

Каталог задается флагом `--office-state-dir`. Профили Claude и Codex не читаются и не пишутся
никогда. Каждый документ проверяется по форме и по размеру перед записью: чужой или слишком
большой payload отклоняется, а прежний файл остается нетронутым.

Из оригинальных настроек убраны три элемента, которые в этом конвейере не могут работать:
`Watch All Sessions` и `Instant Detection (Hooks)` относятся к провайдеру сессий Claude, а внешние
каталоги ассетов подгружает сервер апстрима, которого здесь нет. Они удалены, а не оставлены
переключателями, которые ничего не делают. `+ Agent` и «Open Sessions Folder» скрыты самим
оригиналом в браузерном режиме.

## Как это устроено

```
monitor/pixel-office/
  vendor/                  байт в байт оригинал закрепленного коммита, не редактируется
  vendor-manifest.json     репозиторий, коммит, sha256 и размер каждого файла vendor/
  patches/                 девять именованных патчей: весь локальный слой изменений
  src/projection.mjs       проекция журнала и трассировки в состояния персонажей
  src/office-server.mjs    HTTP, WebSocket и прокси к API журнала
  src/office-state.mjs     локальное хранилище планировки, мест, областей и настроек
  src/assets-build.ts      сборочный декодер ассетов (только Node, только на этапе сборки)
  build.mjs                проверка манифеста, патчи, сборка, граф модулей, провенанс
  vite.config.mjs          вход сборки оригинального фронтенда
  test/                    node --test: проекция, хранилище, маршруты и сокет
  dist/office/             собранный оригинальный интерфейс
  dist/assets.json         предекодированные спрайты и планировка
  dist/build-manifest.json входы, патчи и выходы сборки с хешами
```

Топология запуска: `run_progress.py serve` поднимает свой HTTP-сервер журнала на свободном порту
127.0.0.1, запускает рядом Node-адаптер на запрошенном порту и печатает его URL. Адаптер отдает
офис и `/ws`, а `/details` и `/api/*` проксирует в Python-сервер, который остается единственным
владельцем журнала, трассировки и зарегистрированных артефактов. Ctrl-C и SIGTERM останавливают
обоих: дочерний процесс не переживает лаунчер.

Адаптер только наблюдает. Он опрашивает `/api/events` и `/api/trace` по курсору, у каждого опроса
свой срок, покрывающий и тело ответа, а ответ, пришедший после собственного срока, отбрасывается:
зависший источник становится видимо недоступным, а не устаревшим состоянием, которое все еще
называет себя работой.

### Локальные патчи

Оригинал не редактируется: `vendor/` проверяется по хешам, копируется в `build/`, и уже там
применяются патчи из `patches/`. Каждый патч записан в `dist/build-manifest.json` вместе с хешем
самого патча, хешем оригинала, к которому он применяется, и хешем результата.

| Патч | Зачем |
|---|---|
| `core/asyncapi.yaml`, `core/src/messages.ts` | два серверных сообщения `pipelineActorState` и `pipelineSourceState` и одно клиентское `requestSnapshot` |
| `webview-ui/src/hooks/useExtensionMessages.ts` | нейтральные состояния вместо `agentStatus`, остановка активности при потере сокета, запрос свежего снимка при переподключении |
| `webview-ui/src/office/components/ToolOverlay.tsx` | роль, подпись и происхождение в нативной панели; компактная подпись без наведения и полная при наведении или выборе; цвет точки и пульсация по нейтральному состоянию |
| `webview-ui/src/office/engine/characters.ts` | кадры печати крутятся только у активного персонажа: неактивный сидит в статичной позе вместо того, чтобы печатать все время отдыха за столом |
| `webview-ui/src/components/BottomToolbar.tsx` | одна нативная кнопка `Journal` |
| `webview-ui/src/components/ConnectionIndicator.tsx` | тот же нативный бейдж говорит и о недоступном источнике, а не только о сокете |
| `webview-ui/src/components/SettingsModal.tsx`, `webview-ui/src/App.tsx` | удаление неприменимых элементов настроек и подключение перечисленного выше |

Рендерер, редактор планировки, спрайты, шрифт и композиция не патчатся. В движке изменена ровно
одна ветка: анимация печати. Оригинал усаживает неактивного персонажа за его стол в конце каждой
прогулки и держит его там две-четыре минуты, продолжая крутить кадры печати, - человек, простой,
ошибка, тишина и потерянная связь выглядели бы работой. Расписание прогулок, отдых и все остальные
переходы остались оригинальными; проверка `monitor/pixel-office/test/engine.test.mjs` гоняет
настоящий пропатченный движок по настоящей комнате двадцать минут модельного времени.

### Пересборка

```
cd monitor/pixel-office
npm ci                       # пины из package-lock.json; Node ^20.19.0 || >=22.12.0
npm run build                # печатает хеши патчей и выходов
```

Сборка отказывается работать, если файл `vendor/` разошелся с манифестом, если патч не применяется
к записанному оригиналу, если патч не изменил ни байта, если после патчей отличается файл вне их
списка, если в графе модулей не оказалось оригинальных модулей или появился серверный код апстрима,
или если декодер ассетов что-то пропустил. Чистая пересборка дает те же байты, а исходники сборка
не трогает.

Собранный JavaScript получен из пропатченных оригиналов локальным тулчейном. Он не байт в байт
совпадает с опубликованным npm-пакетом, и `dist/build-manifest.json` это прямо фиксирует.

`dist/` версионируется, поэтому `serve` работает сразу после `git clone` и `npm ci`; `node_modules/`
и временный `build/` - нет.

## Хостинг и границы

Оба сервера слушают только 127.0.0.1 и отказывают запросу с чужим заголовком `Host`. Адаптер отдает
файлы по таблице маршрутов, построенной один раз при старте из `dist/office/` и
`vendor/webview-ui/public/`: общего файлового сервера нет, путь запроса ни с каким каталогом не
склеивается, все остальное - 404. Кроме файлов офиса открыты ровно `/ws`, `/details` и `/api/*`;
`/api/artifact` по-прежнему отдает только зарегистрированные артефакты как инертный текст.

Ни один элемент интерфейса не запускает команд, не устанавливает CLI-хуков и не трогает
пользовательские профили: сообщения `launchAgent`, `setHooksEnabled`, `focusAgent` и `closeAgent`
адаптер игнорирует.

Страница журнала осталась на прежней политике: внешних скриптов у нее теперь нет вовсе, CSP
разрешает только ее собственный инлайновый блок по sha256, `img-src 'none'`, `connect-src 'self'`,
`default-src 'none'` и запрет фреймов.

## Проверки

```
npm --prefix monitor/pixel-office run build
npm --prefix monitor/pixel-office test
python3 -B tests/check_original_office_browser.py --output-root DIR
python3 -B -m unittest discover -s tests
```

`npm test` (node --test) проверяет проекцию журнала в состояния персонажей на фикстурных записях,
локальное хранилище настроек и маршруты с сокетом адаптера на фикстурном источнике: порядок снимка,
переподключение, недоступный источник, тело без конца, отказ чужих сообщений.

`tests/check_original_office_browser.py` водит настоящий Chrome по настоящему `serve`: строит
временный git-репозиторий, замороженный план и локальный фальшивый `codex`, проходит наблюдаемую
сборку, упавшую проверку, проверенный FAIL ревью с нулевым кодом выхода, записанный RETRY, ремонт,
прошедшие проверки и ревью, зарегистрированный разбор, передачу отчета и COMPLETE через шлюз, потом
открывает журнал, теряет связь и восстанавливается. Скриншоты и снятое состояние остаются в
уникальном каталоге под `--output-root`, и путь печатается в конце. Отсутствие Chrome - это провал
ненаблюдаемого офиса, а не пропуск.

`tests/test_pixel_office.py` проверяет провенанс (хеши vendor, применимость и результат каждого
патча, соответствие dist манифесту, состав собранного бандла, оригинальность декодированной
комнаты), точку входа `serve` (маршруты, чужой Host, остановку дочернего процесса) и семантическую
публикацию (расписка проверки, проверенный FAIL ревью, невалидированное ревью, отказ записи без
расписки, неработающий журнал не меняет вердикт команды).
