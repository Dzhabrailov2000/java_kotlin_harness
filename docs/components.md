# Каталог компонентов

Полный состав обвязки с назначением и местом установки. Репозиторий разделен на
общее (`teams/dev`, `shared/skills`, `shared/rules`, `scripts`) и клиентское
(`claude/`, `codex/`): метод, правило и роль существуют в одном экземпляре, а
конфигурация, нативный формат и запуск принадлежат клиенту, который их исполняет.

`install.sh` ставит симлинки: skills из `shared/skills` в `~/.claude/skills/<имя>`,
агентов из `claude/agents` в `~/.claude/agents`, команды, хуки и statusline
пофайлово в соответствующие каталоги `~/.claude`, а общие методы `dev-pipeline`,
`epic-decomposition`, `system-design-tradeoffs` дополнительно в
`~/.agents/skills/<имя>` для Codex. Три роли из `teams/dev` не симлинкуются, а
рендерятся генераторами клиентов: `~/.claude/agents/pipeline-implementer.md` и
`~/.codex/agents/<имя>.toml` из того же канонического Markdown, с профилем и
правами клиента. Установка снимает свои же ссылки на компоненты, которых в репозитории
больше нет (например устаревший `hooks/harness-reminder.js`), переставляет свои
ссылки, оставшиеся от прежней раскладки этого чекаута, и не трогает чужие файлы,
ссылки и `settings.json`. Описания ниже - краткие; полная инструкция каждого
компонента в его файле. Постоянные инструкции для модели (skills, агенты, команды,
шаблоны, workflow) - на английском; ответ пользователю остается русским, а
доменные требования вроде русских комментариев в Kotlin сохраняются.
Происхождение скопированных компонентов - в
[THIRD_PARTY_NOTICES.md](../THIRD_PARTY_NOTICES.md).

## Общие правила

| Файл | Назначение |
| --- | --- |
| shared/rules/simplicity.md | Политика простоты пользователя. Единственный поддерживаемый экземпляр этих семи строк; лаунчеры отправляют файл полным текстом исполнителю и ревьюеру на каждом реальном запуске, включая исправление |
| shared/rules/review-criteria.md | Критерии ревью конвейера: что проверяется, что само по себе не находка (длина функции или файла, поверхностный стиль, спекулятивное усиление), дисциплина severity, ноль находок - валидный итог |

## Роли конвейера

| Роль | Канонический файл | Контекст и профиль | Как попадает в модель |
| --- | --- | --- | --- |
| pipeline-manager | teams/dev/manager.md | свежая сессия Codex на задачу, `gpt-6-astra` / `ultra` | `developer_instructions` процесса `codex exec` плюс абсолютные пути этого чекаута; нативный агент `~/.codex/agents/pipeline-manager.toml` |
| pipeline-implementer | teams/dev/implementer.md | внешняя сессия Claude на попытку, `claude-opus-5` / `max` | добавление к системному промпту вместе с политикой простоты и выбранными skills; нативный агент `~/.claude/agents/pipeline-implementer.md` |
| pipeline-reviewer | teams/dev/reviewer.md | свежая сессия Codex на Check, только чтение, без вложенных агентов, `gpt-6-astra` / `ultra` | голова запроса ревью вместе с критериями ревью и политикой простоты; нативный агент `~/.codex/agents/pipeline-reviewer.toml` |

Текст роли нейтрален к клиенту: в нем только `name`, `description` и инструкции.
Модель, effort, тулы и права живут в генераторах клиентов
(`claude/scripts/install_claude_agents.py`, `codex/scripts/install_codex_agents.py`)
и в флагах лаунчеров. Пути и SHA-256 всего отправленного пишутся в
`invocation.json` (`instruction_sources`, `role_source`). Это доказательство
доставки, а не исполнения: нативный агент - конфигурация порожденной сессии
клиента, корневой `codex exec` получает роль только потому, что ее вписывает
лаунчер, и установленный файл сам по себе не подтверждает, что сессия применила
роль.

| Имя | Назначение | Права |
| --- | --- | --- |

| code-reviewer | Ревью изменений с доказательным гейтом для HIGH/CRITICAL; ноль находок - валидный итог | чтение, Bash для git |
| comment-analyzer | Точность и актуальность комментариев | чтение |
| database-reviewer | Ревью SQL, схем и планов по поставленным свидетельствам; недостающий план - UNVERIFIED | только чтение |
| pr-test-analyzer | Качество и полнота тестового покрытия изменений | чтение, Bash |

их при выборе. Независимый ревьюер конвейера - отдельный контекст Codex
(`gpt-6-astra`, effort `ultra`), а не эти агенты.

## Команды

| Имя | Назначение |
| --- | --- |
| harness | Печатает инвентарь установленной обвязки (запускает `claude/hooks/harness-banner.js`) |
| adr | Завести ADR или сменить статус по конвенциям текущего проекта |
| epic | Разобрать эпик по `epic-decomposition` в формате планирования текущего проекта |
| meeting-notes | Протокол встречи из сырой расшифровки по конвенциям текущего проекта |
| meeting-prep | Prep-документ к встрече по материалам текущего проекта |

Четыре проектные команды находят проект, индекс, конвенции и шаблоны по
аргументам, рабочей директории и инструкциям проекта; в них нет заранее
заданных репозиториев.

## Хуки

| Файл | Когда запускается | Что делает |
| --- | --- | --- |
| harness-banner.js | Вручную, командой `/harness`; как hook не подключен | Печатает инвентарь с описаниями из frontmatter: skills, агенты, команды, события хуков. Идет по симлинкам установки; отсутствующие или битые метаданные пропускает без падения |
| ascii-punctuation.js | PostToolUse для Write и Edit | Проверяет записанный фрагмент на длинное или среднее тире; весь файл не проверяет |

Автоматической вставки каталога в каждый запрос больше нет: каталог выдается
по команде `/harness`, а нужные инструкции менеджер выбирает явно и передает
полным текстом через `--skill`.

Helper `run_claude_task.py` добавляет для вызова исполнителя собственный
PreToolUse hook (`harness_run_audit.py`), который отклоняет невыбранные
Skill, Agent и MCP; в пользовательские настройки он не ставится. Skill, который
существует только ради цикла менеджера или финальной самопроверки
(`dev-pipeline`, `adversarial-self-check`), отклоняется еще раньше, до запуска
модели: эта возможность принадлежит менеджеру. На самостоятельное применение
этих скиллов в других сессиях запрет не распространяется.

## Строка состояния

`claude/statusline/statusline.js`: занятость контекста, лимит сессии на 5 часов и
недельный лимит из payload Claude Code (`context_window`, `rate_limits`);
своего учета не ведет. Включается ключом `statusLine` в `settings.json`.

## Скрипты

| Файл | Назначение |
| --- | --- |
| codex/scripts/run_codex_manager.py | Диспетчеризация менеджера: ровно один процесс `codex exec` с канонической ролью менеджера в `developer_instructions` и абсолютными путями этого чекаута, `instructions.md`, `prompt.md`, `invocation.json`, `result.json`. Песочница и подтверждения берутся из конфигурации Codex машины, если не заданы явные `--sandbox` и `--approval`. Запуск из уже запущенного менеджера отклоняется по маркеру окружения. Цикла, повторов и лимитов нет; `completed` описывает ход CLI, а не приемку |
| codex/scripts/install_codex_agents.py | Генератор нативных агентов Codex из `teams/dev/manager.md` и `teams/dev/reviewer.md`: `name`, `description`, `model`, `model_reasoning_effort`, у ревьюера `sandbox_mode = "read-only"`, и `developer_instructions` - та же сборка, что уходит в корневой `codex exec` (у менеджера с абсолютными путями чекаута, у ревьюера с критериями ревью и политикой простоты). Менеджеру песочница и подтверждения не задаются: спавн наследует права вызвавшей сессии. Своя сгенерированная копия узнается по маркеру и переписывается только при изменении, чужой файл и чужая ссылка сохраняются |
| claude/scripts/install_claude_agents.py | Генератор нативного субагента Claude из `teams/dev/implementer.md`: frontmatter `name`, `description`, `tools`, `model: claude-opus-5`, `effort: max`, тело - роль и политика простоты, как их отправляет лаунчер. Маркер владения и правила сохранения чужого файла те же |
| claude/scripts/run_claude_task.py | Один вызов внешнего исполнителя: обязательные `--acceptance-dir` и `--attempt`, контракт из замороженного плана в отправленном промпте, роль исполнителя, политика простоты и выбранные skills полным текстом в system prompt, `selection.json`, гейт компонентов, doctor, сверка обвязки, `result.json`, журнал прогресса. Чужой workspace, чужой run, непозитивная попытка или попытка сверх явно запрошенного лимита и правленый план отвергаются до запуска CLI. Автоматического таймаута и лимита ходов нет: `--timeout` и `--max-budget-usd` только по явной просьбе пользователя |
| codex/scripts/run_codex_review.py | Ревью Codex: запись ревью без `--acceptance-dir`, терминальная приемочная проверка с ним (роль ревьюера, критерии ревью и политика простоты полным текстом, тот же контракт, run и попытка из плана, сверка baseline до запуска, схема ответа, локальная проверка ответа и квитанция). Таймаута по умолчанию нет |
| claude/scripts/claude_doctor.py | Запуск `claude doctor` после вызова; статус RECORDED / UNVERIFIED означает сбор диагностики, не исправность |
| claude/scripts/harness_run_audit.py | PreToolUse-гейт по выбору менеджера и разбор `events.jsonl`: реальные вызовы против выбора |
| scripts/run_progress.py | Журнал прогресса `progress.jsonl` / `progress.log`, `serve` поднимает офис и API журнала за ним на 127.0.0.1, `emit` для этапов менеджера; `passed` и COMPLETE требуют `--evidence` с квитанцией приемки и явных `--run-id` и `--attempt` этой квитанции. Источник `receipt` пишут захват проверки и приемочное ревью по своей квитанции |
| scripts/run_progress.html | Читаемая сторона офиса: разговор, сессии, метрики и журнал (отдается сервером, внешних ресурсов не грузит) |
| monitor/pixel-office/ | Офис конвейера: закрепленный оригинал Pixel Agents 1.4.1, девять именованных патчей, сборка, адаптер WebSocket и локальное хранилище планировки |
| scripts/role_text.py | Чтение канонических ролей и правил: frontmatter (`name`, `description`), тело для модели, путь и SHA-256 для записи. Общий источник для обоих лаунчеров и генератора нативных агентов |
| scripts/process_group.py | Остановка группы процессов запущенного CLI с ограниченными ожиданиями; общая для лаунчеров, захвата проверок и монитора |
| scripts/run_acceptance.py | Приемка: `plan` замораживает критерии, команды, область и baseline (и то, и другое входит в `plan_id`), `check` захватывает обязательную команду с логами и снимками, `complete` сверяет всю картину вместе с хешами артефактов ревью и выдает квитанцию для COMPLETE. Здесь же единственный рендер контракта задачи, который получают оба запуска |

Helper в PATH не устанавливается; вызывается по пути из корня обвязки.

## Тесты

`python3 -B -m unittest discover -s tests -v`: helper, doctor, сверка обвязки,
монитор прогресса, диспетчеризация менеджера (`tests/test_run_codex_manager.py`:
роль в developer instructions, профиль, сохранение прав машины, отказ от
вложенного менеджера - на локальном фейковом CLI), приемка
(`tests/test_run_acceptance.py`: план, захват проверок, ревью и гейт на
локальном фейковом CLI, без платных вызовов) и установка
(`tests/test_install.py`, только в изолированный `--target-home`).

Офис проверяется отдельно: `npm --prefix monitor/pixel-office run build`,
`npm --prefix monitor/pixel-office test` и
`python3 -B tests/check_original_office_browser.py --output-root <dir>` -
настоящий Chrome по настоящему `serve` на фикстурном конвейере, без платных
вызовов.
