# java_kotlin_harness

Личная обвязка Claude Code и Codex: переносимый набор skills, агентов, команд,
хуков и скриптов, чтобы поднять одинаковую рабочую среду на любой машине и
вести задачи по одному процессу: менеджер готовит задание, внешний Claude
реализует, тесты и независимое ревью решают приемку.

Это единственная точка входа. Подробная процедура менеджера живет в
[инструкции Claude/Codex](shared/skills/dev-pipeline/references/claude-codex.md),
общие правила цикла - в [dev-pipeline](shared/skills/dev-pipeline/SKILL.md), полный
каталог компонентов - в [docs/components.md](docs/components.md), справочник
журнала, трассировки и монитора - в
[docs/observability.md](docs/observability.md).

Постоянные инструкции для модели (skills, агенты, команды, шаблоны, workflow)
написаны по-английски: задания, отчеты исполнителя, ревью и передача замечаний
идут на английском. С пользователем менеджер говорит по-русски и по-русски же
отвечает; цитаты, логи, документы проектов и доменные требования (например
русские комментарии в Kotlin) остаются как есть.

## Что внутри

Общее отделено от клиентского: методы, правила и роли существуют в одном
экземпляре, а каждый клиент держит свою конфигурацию, нативный формат и запуск.

- `teams/dev/` три канонические роли конвейера в одном месте: `manager.md`,
  `implementer.md`, `reviewer.md`. Текст роли нейтрален к клиенту: имя,
  описание и инструкции, без модели, effort, тулов и прав
- `shared/skills/` знание и методы; подключаются по смыслу или явным выбором
  менеджера. `shared/rules/` канонические общие правила: политика простоты
  пользователя и критерии ревью
- `claude/` клиент Claude Code: `agents/` субагенты, `commands/` слэш-команды
  (`/harness`, `/adr`, `/epic`, `/meeting-notes`, `/meeting-prep`), `hooks/`,
  `statusline/`, `scripts/` запуск исполнителя, генератор нативного субагента,
  диагностика и сверка обвязки, `settings.reference.json` (образец, не
  применяется автоматически)
- `codex/` клиент Codex: `scripts/` запуск менеджера, запуск независимого ревью
  и генератор нативных агентов Codex из тех же ролей
- `scripts/` общее для обоих клиентов: приемка, журнал прогресса и монитор,
  трассировка, чтение канонических ролей, остановка группы процессов
- `templates/` шаблоны промпта задачи, ревью, отчета исполнителя и плана приемки
- `docs/` каталог компонентов, маршрут памяти и справочник наблюдаемости
- `install.sh` установка, `tests/` проверки

## Чего здесь нет (намеренно)

Репозиторий обезличен: в нем нет памяти, корпоративных фактов, секретов и
истории сессий; `.gitignore` - страховка от случайного копирования. Знания о
проектах остаются в их репозиториях; личный указатель на источники
необязателен, см. [docs/memory.md](docs/memory.md). Это граница хранения, а не техническая
гарантия: все, что менеджер кладет в промпт или выбранный skill, уходит модели
как обычный запрос. Что передавать, решает менеджер при подготовке задания.

## Установка

    git clone https://github.com/Dzhabrailov2000/java_kotlin_harness.git
    cd java_kotlin_harness
    ./install.sh

Нужны bash и python3 (из него генерируются нативные роли); монитору
дополнительно нужен Node, см. ниже.

`install.sh` симлинкует skills из `shared/skills`, а агентов, команды, хуки и
statusline из `claude/` в `~/.claude`; общие методы `dev-pipeline`,
`epic-decomposition` и `system-design-tradeoffs` дополнительно в
`~/.agents/skills`, чтобы Codex читал тот же исходник. Три роли из `teams/dev/`
ставятся генераторами клиентов из того же канонического Markdown:
`~/.claude/agents/pipeline-implementer.md` с `claude-opus-5`, effort `max` и
тулами исполнителя, `~/.codex/agents/pipeline-manager.toml` и
`pipeline-reviewer.toml` с `gpt-6-astra`, `model_reasoning_effort = "ultra"` и
`sandbox_mode = "read-only"` у ревьюера. Своя сгенерированная копия обновляется
только при изменении, файл, написанный не установкой, не трогается. Существующие файлы и
каталоги, которые не являются симлинками, не перезаписываются, о них печатается
"пропуск"; чужая ссылка тоже сохраняется, а своя ссылка этого чекаута, включая
оставшуюся от прежней раскладки, переставляется на новое место компонента. Свою
же ссылку на компонент, которого в репозитории больше нет (устаревший
`hooks/harness-reminder.js`), установка снимает. Повторный запуск безопасен.
`settings.json` не трогается: сверь его вручную с
`claude/settings.reference.json` и, если в нем остался блок UserPromptSubmit с
`harness-reminder.js`, удали только этот блок.

`./install.sh --target-home <каталог>` ставит обвязку в другой корень. Это
режим для тестов (`tests/test_install.py`), не для обычной работы.

Образец настроек задает профиль конвейера: `claude-opus-5`, effort `xhigh`,
hook ascii-punctuation (PostToolUse Write|Edit), statusline. Каталог обвязки в
каждый запрос больше не подмешивается: его показывает команда `/harness`, а
нужные инструкции менеджер выбирает явно через `--skill`. Флаги `--model` и
`--effort` конкретного запуска главнее файла
настроек; субагенты сохраняют model и tools из своего frontmatter; независимый
ревьюер работает в Codex (`gpt-6-astra`, effort `ultra`) и в этих настройках не
описывается.

## Как идет задача

1. **Пользователь ставит задачу фронтенд-сессии** - Claude Code или Codex, любой
   из двух. Пример запроса: "Выполни задачу <ID> из <файл или ссылка>: Claude
   реализует с нашей обвязкой, проверка через dev-pipeline, отчет мне после
   каждой итерации".
2. **Фронтенд передает задачу разработки менеджеру и на этом выходит из
   процесса.** Вход один для обоих клиентов - skill dev-pipeline. Он различает
   режимы: документ, отчет или исследование проверяются в самой сессии агентами
   builder и judge, а запрос на разработку кода уходит менеджеру - маленький
   отчет отдельного менеджера не получает. Для разработки фронтенд запускает
   `codex/scripts/run_codex_manager.py`, ровно один свежий контекст Codex
   (`gpt-6-astra`, effort `ultra`) с канонической ролью менеджера в developer
   instructions. Песочница и политика подтверждений берутся из конфигурации
   Codex этой машины: лаунчер их не переопределяет, отдельный выбор на запуск
   задается явными `--sandbox` и `--approval` и записывается. Менеджер не
   запускает второго менеджера: попытка отклоняется по маркеру в окружении.
   Нулевой код возврата лаунчера означает завершившийся процесс, а не принятую
   задачу.
3. **Менеджер изучает проект и замораживает контракт.** Читает задачу, код,
   применимые инструкции (AGENTS.md / CLAUDE.md / README) и названные задачей
   документы, а если он есть - и личный указатель на источники, который
   необязателен; фиксирует Define
   и один раз замораживает план приемки: критерии с ID, обязательные проверки с
   точным argv, разрешенные и защищенные пути, run и лимит попыток, если
   пользователь его назвал (по умолчанию `max_attempts` пустой - квоты нет). Явно
   выбирает компоненты: skills через `--skill`, нужных агентов через `--agent`,
   MCP через `--mcp-config`, с причиной для каждого. Промпт по
   [templates/task.md](templates/task.md) несет человеческую часть задачи:
   критерии и область в него не переписываются, их добавляет запуск из плана.
4. **Внешний Claude реализует.** `claude/scripts/run_claude_task.py` запускает
   один вызов исполнителя. Выбранный конвейером профиль - `claude-opus-5` /
   `max`, менеджер передает его флагами `--model` и `--effort`; неизмененный
   умолчательный effort самого лаунчера - `xhigh`. Автоматических
   ограничений у вызова нет: ни таймаута, ни лимита ходов, токенов или денег -
   вызов идет до завершения CLI или до прерывания пользователем, а `--timeout` и
   `--max-budget-usd` передаются только тогда, когда пользователь сам их
   попросил. Запуск реализации требует
   `--acceptance-dir` и `--attempt`: план проверяется до старта CLI (чужой
   workspace, чужой run, непозитивная попытка или попытка сверх явно
   запрошенного лимита и правленый план отвергаются), а
   его контракт уходит в промпт вместе с заданием и сохраняется как
   `prompt.md`. Helper передает полным текстом роль исполнителя
   (`teams/dev/implementer.md`), политику простоты пользователя
   (`shared/rules/simplicity.md`) и выбранные skills, пишет их пути и SHA-256 в
   `invocation.json`, фиксирует выбор в `selection.json` и блокирует невыбранные
   Skill, Agent и MCP. Skill, который существует только ради цикла менеджера или
   финального самопроверочного прохода (`dev-pipeline`,
   `adversarial-self-check`), отклоняется до запуска модели. Исполнитель
   не расширяет набор, не ведет dev-pipeline, не запускает внешнее ревью и не
   добавляет финальный цикл самопроверки; недостающую возможность возвращает
   менеджеру. Отчет - по
   [templates/implementation-report.md](templates/implementation-report.md),
   с основаниями: команды, exit code, file:line.
5. **Менеджер проверяет.** После каждого вызова helper сохраняет `claude doctor`
   и `harness-audit.json`: это диагностика установки и сверка реальных вызовов
   с выбором, не приемка. `completed: false` в `result.json` - результат CLI,
   а не доказательство дефекта кода. Приемку определяют захваченные проверки
   плана (тесты, компиляция, свои проверки проекта - под тем именем, что они
   действительно выполняют) и независимое ревью в новом контексте Codex
   (`gpt-6-astra`, `ultra`) по `claude/agents/code-reviewer.md` и критериям задачи.
   Обязательные проверки запускаются через `scripts/run_acceptance.py check` по
   замороженному плану: `passed` - это наблюдение за процессом (exit 0, без
   таймаута и прерывания, исходники не менялись), а не отметка человека или
   модели. Ревью отдельно отвечает, ловят ли тесты неверную реализацию.
6. **Полный отчет возвращается исполнителю дословно** с решениями менеджера по
   каждому замечанию: CONFIRMED, REFUTED или UNVERIFIED. Правятся только
   подтвержденные; повторный вопрос не является замечанием. После правок -
   полный Check заново.
7. **Явное завершение.** COMPLETE только для проверенной версии: все критерии
   покрыты, Critical = 0, Major = 0, ключевых UNVERIFIED нет. Решение проходит
   через гейт `scripts/run_acceptance.py complete`, который заново снимает
   рабочую копию и сверяет план, квитанции проверок, проверенное ревью и
   область изменений; `emit --phase decision --status complete` без этой
   квитанции отвергается. Иначе RETRY, VERIFY или ESCALATE с вопросами
   человеку. Квоты попыток по умолчанию нет: номер попытки нужен для
   доказательств, а цикл останавливают приемка, прерывание пользователя,
   реальный блокер или лимит, который пользователь задал сам.
   Подтвержденный дефект реализации -
   это RETRY, нехватка основания - ограниченный VERIFY, а изменение самих
   требований - новый контракт с основанием, а не правка замороженного плана.
   Финальный handoff - `--read-only`, без правок. Commit, push и активация в
   реальном доме - только в авторизованном объеме. Что остается после задачи и
   где, включая короткий разбор итога, описано в
   [docs/memory.md](docs/memory.md).

Живой монитор: helper ведет `progress.jsonl` и `progress.log` (по умолчанию в
`--output-dir`; общий `--progress-dir` связывает вызовы одной задачи),
`python3 scripts/run_progress.py serve --progress-dir <dir>` поднимает на
127.0.0.1 офис конвейера - оригинальный интерфейс Pixel Agents 1.4.1 - и
печатает один URL; читаемый журнал открывается кнопкой `Journal` и по адресу
`<URL>/details`. Для офиса нужны Node `^20.19.0 || >=22.12.0` (диапазон
закрепленного Vite; он же записан в `engines` пакета) и `npm ci --prefix
monitor/pixel-office`; подробности - в
[docs/monitor-office.md](docs/monitor-office.md). `emit` пишет этапы менеджера,
а захват проверки и приемочное ревью публикуют собственный результат по своей
запечатанной квитанции. Рядом с журналом helper
ведет `trace.jsonl`: промпт задачи, публичные ответы модели и usage токенов;
`codex/scripts/run_codex_review.py` так же записывает ревью Codex, а
`scripts/run_trace.py` регистрирует запрос пользователя, замечания и решения
менеджера и импортирует старые журналы вместе с артефактами запуска. Helper
записывает и выбранную обвязку каждого вызова (скиллы, агенты, MCP с hash
источников), наблюдаемые вызовы компонентов, статусы `claude doctor` и сверки;
для каждой сессии Claude и Codex страница показывает идентификатор, емкость
окна контекста и приближение занятости, а неизвестное называет неизвестным.
Страница показывает этапы по попыткам, разговор, токены, лимиты и блок по
каждому вызову LLM. Поля, статусы, команды записи и ограничения - в
[docs/observability.md](docs/observability.md).

Приемка ведется отдельно от журнала: `scripts/run_acceptance.py` замораживает
план задачи с критериями, командами и областью, снимает исходное состояние
рабочей копии, захватывает каждую обязательную проверку вместе с логами и их
hash и закрывает COMPLETE только при связной картине из плана, снимка, квитанций
и проверенного ревью. План опознается вместе с baseline, на котором заморожен,
а файлы ревью хешируются заново перед каждым решением. Тот же план - источник
задания: его контракт рендерится один раз и уходит и исполнителю, и ревьюеру,
поэтому две роли не могут получить разные требования. Ревью приемки запускается
тем же `run_codex_review.py` с `--acceptance-dir`: ревьюеру передается роль
терминальной проверки на фиксированном профиле, ответ запрашивается через
`--output-schema` и проверяется локально. Это защита от
устаревших и ничем не подкрепленных утверждений в поддерживаемом потоке команд,
а не подпись: тот, кто перепишет и код, и план, и все квитанции, обойдет и ее.
Команды по шагам - в [инструкции менеджера](shared/skills/dev-pipeline/references/claude-codex.md#acceptance-plan-captured-checks-review-and-the-complete-gate).

## Состав

Кратко; полный каталог с назначением каждого компонента - в
[docs/components.md](docs/components.md).

- Skills предметные: api-design, architecture-decision-records,
  database-migrations, hexagonal-architecture, kotlin-comment-style,
  kotlin-coroutines-flows, kotlin-patterns, kotlin-testing, postgres-patterns.
- Skills-методы: epic-decomposition, system-design-tradeoffs.
- Skills дисциплины: scope-fence, evidence-before-claim, adversarial-self-check,
  lead-with-outcome, context-hygiene, dev-pipeline.
- Общие правила: simplicity (политика простоты пользователя, уходит исполнителю
  и ревьюеру полным текстом), review-criteria (критерии ревью конвейера).
- Роли конвейера в `teams/dev/`: manager, implementer, reviewer; один
  поддерживаемый текст на роль, из него же генератор клиента делает нативного
  агента с моделью, effort, тулами и правами.
- Агенты: builder, judge, code-architect, code-explorer, code-reviewer,
  comment-analyzer, database-reviewer, pr-test-analyzer, silent-failure-hunter,
  type-design-analyzer.
- Команды: harness, adr, epic, meeting-notes, meeting-prep.
- Хуки: harness-banner (по `/harness`, как hook не подключен: печатает
  каталог с описаниями по запросу), ascii-punctuation (PostToolUse Write|Edit:
  проверяет записанный фрагмент, не весь файл).
- Statusline: занятость контекста, лимит сессии на 5 часов, недельный лимит.
- Скрипты: `claude/scripts/` run_claude_task.py, claude_doctor.py,
  harness_run_audit.py, install_claude_agents.py; `codex/scripts/`
  run_codex_manager.py, run_codex_review.py, install_codex_agents.py; `scripts/` run_acceptance.py,
  run_progress.py, run_trace.py, role_text.py, process_group.py.

Проверки: `python3 -B -m unittest discover -s tests -v`.

Часть агентов и skills скопирована из Everything Claude Code и адаптирована;
точный список и лицензия - в [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md).
