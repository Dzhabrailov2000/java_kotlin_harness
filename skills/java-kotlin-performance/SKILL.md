# Производительность по измерению

Установи проблемный путь и критерий результата. В ревью предложи правки;
выполняй их по задаче. Не объявляй короткий код быстрым или длинный код медленным по внешнему виду.

## Зафиксируй эксперимент

Назови нагрузку, размер данных, версию JVM/БД, warmup, число измерений и нужную величину:
latency, throughput, allocation, память или количество I/O. Сначала получи baseline.
Этот порядок - методика навыка, не обещание универсального benchmark-рецепта.

## Найди реальную стоимость

- **Контракт JDK Stream:** parallel execution требует правильной reduction и не дает
  универсальной гарантии ускорения. **Контракт Kotlin:** Sequence добавляет overhead и может
  проиграть на малом/simple pipeline. Выбери по существенному измерению. [S1] [S2]
- **Выбор навыка:** прежде чем менять локальный цикл, проверь повторные SQL/HTTP, объем данных,
  поиск внутри обхода и удерживаемые ресурсы. Обоснуй структуру данных входом и операциями.
- **Пример JMH:** неиспользуемый результат может быть устранен JIT; возвращай результат или
  применяй подходящий Blackhole, чтобы измерять нужную работу. [S3]
- **Пример JMH:** предсказуемая константная работа может быть свернута компилятором.
  Сохрани реалистичные входы и проверь, что benchmark не измеряет уже вычисленную константу. [S4]
- **Контракт PostgreSQL:** EXPLAIN показывает план и оценки; EXPLAIN ANALYZE исполняет запрос
  и показывает фактические данные. Не запускай изменяющий ANALYZE на живых данных без полномочий. [S5]
- **Выбор навыка:** сравнивай до/после при одинаковом сценарии; учитывай ошибки и стоимость
  записи/памяти. Не принимай ускорение за улучшение, если оно теряет порядок или корректность.
- **Выбор навыка:** сначала используй имеющийся profiler/benchmark. Не добавляй framework,
  кэш, pooling или специализированную коллекцию без измеримой причины и цены сопровождения.

## Пример JMH

Адаптация примера DeadCode: результат нужно сделать наблюдаемым. [S3]

~~~java
@Benchmark
public double measureSqrt() {
    return Math.sqrt(input);
}
~~~

Это метод внутри JMH state, где `input` - изменяемое поле состояния с подходящими входами.
Сам фрагмент не задает полный benchmark: сохрани warmup, forks и параметры используемого harness.
Не превращай input в заведомую compile-time константу. [S3] [S4]

## Проверь и сообщи

Назови команду, окружение, baseline, результат и ограничения измерения. Microbenchmark stdlib
не объявляй доказательством latency целого endpoint: проверь нужный уровень отдельно.
В ревью отдели доказанную деградацию от гипотезы и предложи эксперимент. Сохрани читаемость,
если измеримый выигрыш не нужен задаче или не подтвержден.
