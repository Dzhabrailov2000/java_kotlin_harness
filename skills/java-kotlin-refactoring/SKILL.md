# Рефакторинг и читаемость

Упрости понимание конкретного сценария. В ревью предложи правки; выполняй их, когда задача
включает изменение кода. Порядок работы ниже - методика навыка, не универсальная норма автора.

## Установи обещанное поведение

- Прочитай вызовы, ошибки, эффекты, порядок обработки, транзакции и отмену. Опиши, что сохраняешь.
- Отдели исправление дефекта от структурной правки. По определению Fowler рефакторинг сохраняет
  наблюдаемое поведение; изменение статуса HTTP или правила округления этим определением не покрывается. [S1]
- Найди конкретную трудность чтения: смешанные уровни, скрытую мутацию, неясное условие или роли данных.
  Не вводи свой лимит строк, параметров или вложенности как доказательство плохого кода; лимиты, уже
  принятые в правилах проекта, соблюдай.

## Выбери минимальное преобразование

- **Прием Fowler:** выдели связное вычисление в функцию, названную по намерению. Это полезно,
  если имя объясняет шаг; отдельная функция для каждого выражения не является целью. [S2]
- **Прием Fowler:** вынеси особые исходы в guard clauses, если основная ветвь становится яснее.
  Сохрани порядок проверок и эффектов; пример из каталога не доказывает безопасность любой перестановки. [S3]
- **Выбор навыка:** предпочти локальные именованные значения цепочке вложенных `let/run/also`,
  когда читателю приходится восстанавливать получателя и смысл каждого результата.
- **Выбор навыка:** объединяй дублирование, когда совпадают правило и причина его изменения.
  Похожий текст двух разных правил не обязывает создавать общий generic framework.
- **Контракт API:** перенос вычисления между обычной коллекцией, Sequence и Stream меняет момент
  исполнения; Java Stream может исключать ненужные промежуточные этапы. Сохрани нужные эффекты. [S4] [S5]
- **Контракт Spring:** извлечение метода в bean может изменить proxy-перехват; self-invocation
  в обычном proxy-режиме обходит advice. Проверь транзакции/безопасность при такой правке. [S6]
- **Выбор навыка:** раздели большой переход на проверяемые шаги. Не добавляй слой, интерфейс,
  DSL или новую библиотеку, если задача решается понятной функцией и существующими типами.

## Пример

Адаптация Extract Function из каталога Fowler: дай промежуточному действию имя. Это схема,
а не код неизвестного проекта. [S2]

~~~kotlin
fun printInvoice(invoice: Invoice) {
    printBanner()
    printDetails(invoice.outstandingAmount())
}
~~~

`Invoice`, `printBanner` и `printDetails` здесь иллюстративны. Не переноси реальные побочные
эффекты внутрь `outstandingAmount` ради сходства с примером; сначала установи их контракт.

## Проверь и сообщи

Сравни существенные результаты и порядок эффектов до/после. Используй существующие тесты,
добавляя сценарий только для реального риска. Для proxy, SQL или ленивого I/O проверь эту границу.
В находке назови конкретную трудность, предложенное упрощение и сохраняемые гарантии.
Если функция уже читается ясно, оставь ее. Отдели выполненную проверку от предложенной.
